## TL;DR
Size systems from **peak concurrency**, **RAM working set**, and **storage + backup retention**—not guesses. Scale **vertically** until a single box genuinely hurts, include **your own ops hours** when comparing managed vs self-hosted bills, and pick the simplest runtime that fits (for this static site, **Cloudflare Workers** beats a VPS and makes **Kubernetes** pure overhead).

## Why it exists
Teams routinely burn money in two opposite ways: over-provisioning a multi-node Kubernetes cluster for a site that gets 500 visits a day, or under-sizing a tiny single-core VM whose database swaps to disk the first time a post hits a news aggregator.

## Mental model
Total cost of ownership (TCO) = **compute/bandwidth bill + ops hours × hourly rate + downtime risk**. Every extra moving part (clusters, brokers, self-hosted DBs) trades monthly cloud spend for your engineering time.

## Core concepts

### 1. Estimating CPU, RAM, and storage from traffic
Use back-of-the-envelope capacity math before buying hardware:
- **CPU:** `peak_rps = avg_rps × peak_multiplier` (often 3–5× for spiky traffic). Multiply by average CPU time per request (`10 ms` CPU time at `100 RPS` needs at least `1.0` full core, so target `2+` vCPUs for headroom).
- **RAM:** Sum your app runtime footprint + connection pools + **database hot working set** (active B-tree indexes and hot rows). When Postgres indexes spill out of RAM to disk, p99 latency spikes sharply.
- **Storage:** Active table size + index overhead + WAL/logs + **backup retention** (if you keep 7 daily snapshots, budget for growth and restore space, not just today's `df -h`).

### 2. Vertical vs horizontal scaling
- **Vertical scaling (scale up):** Upgrade from 2 vCPU / 4 GB RAM to 8 vCPU / 32 GB RAM. Zero code changes, no distributed locks, and a single Postgres primary handles far more traffic than most apps ever see. Trade-off: brief restart downtime on resize and an eventual hardware ceiling.
- **Horizontal scaling (scale out):** Run N stateless replicas behind a load balancer. Requires externalizing sessions/uploads (Redis, object storage) and handling DB connection pooling. Necessary for zero-downtime rolling deploys, multi-AZ high availability, or exceeding one machine's limits.

### 3. Managed vs self-hosted cost (including your own time)
A bare VPS looks cheaper on paper than a managed database or serverless platform—until you add:
- OS & security patching, TLS automation, and firewall hardening.
- Automated backups, off-site replication, and periodic restore drills.
- Debugging disk-full alerts or OOMKills outside work hours.
If you are a solo builder or small product team, paying a modest managed-service premium often buys back dozens of engineering hours a month.

### 4. Worked example: this site on Cloudflare Workers vs VPS vs Kubernetes
| Option | What runs | Ops burden | Fit for Mengty Learns |
|---|---|---|---|
| **Cloudflare Workers** (`@opennextjs/cloudflare`) | Static HTML/CSS/JS + `cards.json` served from global edge cache | Near zero (git push → CI build → deploy) | **Best fit:** sub-second global loads, zero idle server, no OS/TLS/firewall maintenance |
| **Single Ubuntu VPS** (Caddy + Node/static) | 1 VM running Caddy serving static files | Medium (SSH hardening, `ufw`, `unattended-upgrades`, monitoring) | **Viable, unnecessary:** you pay monthly for an idle VM and own OS patching for static files |
| **Kubernetes cluster** (EKS/GKE/self-managed) | Control plane + worker nodes + Ingress + cert-manager + Deployments | High (cluster upgrades, YAML, RBAC, probes, observability) | **Overkill:** pays control-plane/node overhead and constant maintenance for zero dynamic scaling need |

## When you DON'T need this
- **Pre-revenue / < 1,000 daily users:** Don't spend a week building spreadsheets or load-testing—pick the smallest tier on a managed platform or a single small VPS and add basic CPU/memory alerts.
- **Static sites with no backend:** Edge CDNs and Workers scale to massive traffic spikes automatically with zero capacity planning.
- **Cost / complexity trade-off:** Upfront sizing prevents surprise cloud bills and OOM crashes, while over-optimizing early wastes engineering time that should go into shipping features.

## Gotchas
- **Sizing for average traffic instead of peak:** A site averaging 2 RPS can still hit 50 RPS for 10 minutes after a link goes viral.
- **Forgetting egress bandwidth charges:** Some cloud providers charge steeply per GB of outbound transfer, while static assets on edge CDNs avoid per-GB origin egress surprises.
- **Assuming Kubernetes saves money:** Without dozens of microservices packing bin-packed nodes, Kubernetes usually *increases* both cloud bill and engineering overhead.

## Production checklist
- [ ] Static assets and cacheable pages are served from a CDN/edge rather than origin compute.
- [ ] Database RAM is sized to hold active indexes in memory.
- [ ] Alerts fire on sustained CPU, memory pressure, and disk usage > 80% before outages hit.
- [ ] Infrastructure choice matches team size—no Kubernetes unless multi-service / multi-team requirements justify it.
