## TL;DR
Loading an `https://` URL is a layered handoff: **DNS** resolves the hostname to an IP, **TCP** establishes a reliable byte stream with a 3-way handshake, **TLS 1.3** authenticates the server and encrypts the channel in 1-RTT, and **HTTP** exchanges requests and responses inside that tunnel.

## Intent
<Intent>
Trace every network layer between typing a URL in a browser and receiving an HTTP `200 OK` response, so you can pinpoint whether a failure is DNS, TCP, TLS, or HTTP.
</Intent>

## Problem
When a web request fails or feels slow, "the network is down" is rarely actionable. Without knowing which layer runs first—name resolution, transport connection, encryption handshake, or application framing—it is hard to tell a `NXDOMAIN` lookup failure apart from a blocked TCP port, an expired TLS certificate, or a `502` HTTP gateway error.

## Solution
Each protocol solves one narrow job and hands off to the next:

1. **DNS (Domain Name System):** The client asks a recursive resolver for the `A` (IPv4) or `AAAA` (IPv6) record of the hostname. Cached results are reused until their TTL expires.
2. **TCP (RFC 9293):** The client opens a socket to the resolved IP on port `443` using the 3-way handshake (`SYN` → `SYN-ACK` → `ACK`), establishing sequence numbers for ordered, retransmitted byte delivery.
3. **TLS 1.3 (RFC 8446):** Inside the TCP stream, `ClientHello` and `ServerHello` negotiate a cipher suite and Diffie-Hellman key share in **1-RTT**, verify the server's X.509 certificate chain, and derive symmetric session keys.
4. **HTTP (RFC 9110):** Once the TLS record layer is open, the browser sends an HTTP request (`GET / HTTP/1.1` or HTTP/2 `HEADERS` frame) and the server returns status code, headers, and body back down the same TLS and TCP stack.

## Real-world analogy
<Analogy>
Think of calling a business: **DNS** is looking up their phone number in a directory; **TCP** is dialing and hearing "Hello, can you hear me?" / "Yes, I hear you"; **TLS** is switching to a shared code language after checking their ID badge; and **HTTP** is the actual conversation ("Send me invoice #42" / "Here it is").
</Analogy>

## Code
You can observe each stage directly with `curl -v` (verbose output prints DNS resolution, TCP connect, TLS handshake, and HTTP headers):

```bash
# Inspect DNS, TCP connect, TLS 1.3 negotiation, and HTTP response headers (not run)
curl -vI --tlsv1.3 https://example.com
```

## How to implement
<Steps>
  <Step>
    ### Check DNS resolution first
    Verify the hostname resolves to the expected IP (`dig +short example.com` or `nslookup example.com`).
  </Step>
  <Step>
    ### Verify TCP reachability
    Confirm the target IP and port (`443`) accept connections without firewall drops.
  </Step>
  <Step>
    ### Inspect TLS certificate and version
    Check that the server presents a valid certificate chain and negotiates TLS 1.2 or TLS 1.3.
  </Step>
  <Step>
    ### Read the HTTP status and headers
    Inspect the HTTP status code, `Cache-Control`, and `Content-Type` returned by the origin.
  </Step>
</Steps>

## Pros / Cons
<ProsCons
  pros={[
    'Clean separation of concerns: DNS, TCP, TLS, and HTTP evolve independently.',
    'TLS 1.3 cuts handshake latency to 1-RTT (and 0-RTT for resumed sessions with replay caveats).',
    'Standardized RFCs mean any compliant browser, CLI, or proxy interoperates.',
  ]}
  cons={[
    'Cold connections pay sequential round trips (DNS + TCP + TLS) before the first HTTP byte.',
    'Head-of-line blocking in TCP delays all multiplexed HTTP/2 streams if one packet drops (why HTTP/3 uses QUIC over UDP).',
  ]}
/>
