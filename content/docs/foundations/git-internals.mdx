## TL;DR
Git is a **content-addressable filesystem**: files are **blobs**, directories are **trees**, snapshots are **commits**, and branches are just **41-byte pointer files** (`refs`). **Merge** joins two histories with a new merge commit; **rebase** replays your commits onto a new base, producing brand-new commit hashes.

## Intent
<Intent>
Understand what Git actually stores in `.git/objects` and `.git/refs`, so branches, `HEAD`, `merge`, and `rebase` stop feeling like magic when history diverges or a rebase conflicts.
</Intent>

## Problem
Treating Git as a sequence of diffs or folders makes `detached HEAD`, `fast-forward`, and `rebase` force-pushes terrifying. Without knowing that branches are mutable pointers to immutable commits, developers accidentally rewrite shared history or lose track of dangling commits.

## Solution
Every object in `.git/objects` is hashed (SHA-1 by default) and immutable:

- **Blob:** raw compressed file content (no filename or permissions). Identical files across commits share one blob.
- **Tree:** maps filenames and modes to blobs and subtrees.
- **Commit:** points to one root **tree**, zero or more **parent** commits, plus author, committer, and message.
- **Branch (`refs/heads/<name>`):** a plain file containing a commit hash. `HEAD` is usually a symbolic ref pointing to the current branch.

Because commits are immutable, **merging** `feature` into `main` creates a new commit with two parents (`main` tip and `feature` tip). **Rebasing** `feature` onto `main` computes the diff of each commit on `feature` and applies them one by one on top of `main`, generating **new commit hashes** (`f1'` and `f2'`) and moving the `feature` branch pointer.

## Real-world analogy
<Analogy>
Think of commits as **immutable ledger pages** and branches as **sticky notes** placed on the latest page. Merging staples two branches together on a new summary page. Rebasing copies your draft pages onto fresh paper after someone else's pages, giving your copies new page numbers.
</Analogy>

## Code
Inspect real Git objects directly in a repository with plumbing commands (`git cat-file`, `git rev-parse`):

```bash
# Verified with git 2.54.0.windows.1 in this repo
git rev-parse HEAD
# Inspect the commit object (tree, parent, author, message)
git cat-file -p HEAD
# Inspect the root tree pointed to by HEAD
git cat-file -p HEAD^{tree}
```

```bash
# Rebase feature onto updated main (not run)
git switch feature
git rebase main
```

## How to implement
<Steps>
  <Step>
    ### Check your branch state
    Run `git status` and `git log --oneline --graph -n 10` before rewriting anything.
  </Step>
  <Step>
    ### Rebase local commits cleanly
    Run `git fetch origin && git rebase origin/main`. Resolve any conflict per commit, then `git rebase --continue`.
  </Step>
  <Step>
    ### Recover safely if needed
    If a rebase goes wrong, run `git rebase --abort` during the rebase, or `git reflog` afterward to reset to the old hash.
  </Step>
</Steps>
