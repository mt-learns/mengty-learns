## TL;DR
A **reverse proxy** sits in front of your app servers to handle **TLS termination** (via **ACME / Let's Encrypt**), virtual-host routing, compression, and forwarding headers (`Host`, `X-Forwarded-For`, `X-Forwarded-Proto`). Pick **Caddy** for zero-config HTTPS on a single server, **Nginx** for high-throughput tuning, or a **managed edge** (Cloudflare) when you don't want to run a proxy VM at all.

## Intent
<Intent>
Understand what a reverse proxy does at the edge of your backend, how ACME automates TLS certificates, and when to choose Nginx, Caddy, or a managed edge.
</Intent>

## Problem
Application runtimes (Node.js, Go, Python) are built to run business logic, not to juggle TLS certificates, HTTP/2/HTTP/3 upgrades, gzip/Brotli compression, or host-based routing across multiple services on port `443`. Exposing app ports directly forces every service to manage certificates and leaves them open to slow-client attacks.

## Solution
Place a reverse proxy on ports `80`/`443` while keeping upstream apps bound to `127.0.0.1` or a private network:

1. **TLS termination & ACME:** The proxy proves domain ownership to a Certificate Authority (like Let's Encrypt) via **ACME** (`HTTP-01` challenge on port `80` or `DNS-01` TXT record), obtains a short-lived certificate, and renews it automatically before expiry.
2. **Routing & headers:** The proxy inspects `Host` and path, forwards requests to the right upstream (`127.0.0.1:3000`), and passes `Host`, `X-Forwarded-For`, and `X-Forwarded-Proto` so the app knows the original client IP and scheme.
3. **Compression & buffering:** The proxy compresses responses (`gzip`/`zstd`) and buffers slow clients so upstream worker threads aren't tied up waiting on mobile networks.

| Option | Strengths | Trade-offs |
|---|---|---|
| **Caddy** | Automatic ACME HTTPS, HTTP/3, tiny `Caddyfile` | Smaller third-party module ecosystem than Nginx |
| **Nginx** | Battle-tested performance, rich directive control | Manual Certbot/ACME setup and reload plumbing |
| **Managed edge (Cloudflare)** | Anycast DDoS protection, auto certs, zero VM upkeep | Vendor coupling; traffic passes through third-party edge |

## Real-world analogy
<Analogy>
A reverse proxy is like a building's **security reception desk**: visitors present their ID at one front door (**port 443 / TLS**), the desk logs who they are (`X-Forwarded-For`) and sends them to the right internal suite (`:3000` or `:8080`), while the teams inside never have to guard the street entrance themselves.
</Analogy>

## Code
Compare a minimal **Caddyfile** (automatic HTTPS included) with a minimal **Nginx** `server` block (paired with Certbot certificates):

<Tabs items={['Caddyfile', 'Nginx']}>
  <Tab value="Caddyfile">
```text
# /etc/caddy/Caddyfile (not run)
app.example.com {
    encode zstd gzip
    reverse_proxy 127.0.0.1:3000
}
```
  </Tab>
  <Tab value="Nginx">
```nginx
# /etc/nginx/conf.d/app.conf (not run)
server {
    listen 443 ssl;
    http2 on;
    server_name app.example.com;

    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```
  </Tab>
</Tabs>

## When you DON'T need this
- **Static sites on a managed edge (like this site):** Cloudflare Workers/Pages or Vercel already terminate TLS, issue certificates, and compress assets—running Nginx in front would add a redundant hop and a VM to patch.
- **Internal cluster-only services:** If a service is only called by other Pods inside a private VPC or service mesh, you don't need a public-facing Nginx/Caddy instance on every node.
- **Cost / complexity trade-off:** Running your own Caddy/Nginx on a VM is cheap ($5–$10/mo), but you own OS patching, firewall rules (`80`/`443` open, `3000` blocked externally), and certificate renewal alerts. A managed load balancer or edge eliminates VM maintenance in exchange for per-hour or per-request pricing.

<Checklist

## How to implement
<Steps>
  <Step>
    ### Bind the upstream app to loopback or a private network
    Listen on `127.0.0.1:3000` (or an internal Docker network) so callers cannot bypass the proxy.
  </Step>
  <Step>
    ### Configure ACME TLS and forwarding headers
    Point DNS `A`/`AAAA` records to the proxy, open ports `80` and `443`, and forward `Host`, `X-Forwarded-For`, and `X-Forwarded-Proto`.
  </Step>
  <Step>
    ### Test renewal and headers
    Verify `curl -I https://app.example.com` shows a valid certificate and that your app reads `X-Forwarded-Proto` safely only from trusted proxy IPs.
  </Step>
</Steps>
