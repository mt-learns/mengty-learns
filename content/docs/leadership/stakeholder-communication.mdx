## TL;DR
Non-engineers optimize for **cost, risk, and customer outcomes**—not code mechanisms. Lead with the **consequence and a number** (BLUF), frame estimates as **ranges with named assumptions**, and offer **trade-offs** instead of a flat "no."

## Why it exists
An accurate technical warning—*"we have an N+1 query and technical debt"*—often gets ignored for months because non-technical leaders hear *"engineering wants time to tidy up."* Translating the mechanism into business impact lets stakeholders fund fixes before a peak-traffic outage hits.

## Mental model: Pick one framing by audience

| Audience | What they are measured on | Framing that lands |
|---|---|---|
| **Finance / Budget** | Cost, unit economics, payback | *"X costs 8 days per feature today; 5 days of cleanup halves the next four features."* |
| **Risk / Compliance / Ops** | Likelihood, consequence, control | *"Concurrent edits can overwrite settlement totals silently; 4 days adds optimistic locking."* |
| **PM / PO / Commercial** | Customer impact, dates, scope | *"At 40x peak volume, checkout slows to 25s and misses our SLA window for 10,000 orders."* |

## Do it: Technical-to-business translation table

| What engineers say | What stakeholders hear | Say instead |
|---|---|---|
| *"We have technical debt."* | *"You want time to tidy up."* | *"Every new rule costs 8 days instead of 3 because the logic is duplicated in three services."* |
| *"There's an N+1 query."* | *(Nothing actionable)* | *"One order triggers 40 DB reads instead of 1. Fine today; at peak sale volume it stalls the batch past 09:00."* |
| *"We need a 2-day spike."* | *"You want to research instead of ship."* | *"Two days to confirm if the vendor supports batching—that answer separates a 2-week build from a 6-week build."* |
| *"That test is flaky."* | *"Your tests don't work."* | *"One test fails 5% of the time unrelated to changes, training people to ignore real CI failures. One day fixes it."* |
| *"We'll roll back if needed."* | *"Press undo and nothing breaks."* | *"We can revert code in 60 seconds, but records already written under the new rule still need a manual check."* |
| *"Probably three weeks."* | *"Three weeks—committed."* | *"Two to four weeks: two if the API supports batches, four if we build a queue. I'll confirm by Thursday."* |

### Saying "no" with options
Never hand a PM a dead end. Offer one of four paths:
1. **Trade:** *"Yes, and it pushes the CSV export out by one sprint. Your call."*
2. **Split:** *"The core flow for the two waiting accounts takes 1 week; bulk automation takes 4."*
3. **Defer with a trigger:** *"Not now—revisit when daily volume crosses 1,000 orders."*
4. **Manual bridge:** *"A supported admin script solves this by Friday while we evaluate full automation."*

## Gotchas
- **Leading with the mechanism:** Put the customer/business consequence in sentence one; offer the technical mechanism only if asked.
- **Hedging words without dates:** *"Maybe," "probably,"* and *"kind of"* erode credibility. Replace them with a range, confidence level, or *"I'll confirm by [date]."*
- **Mixing all three framings:** Pick the one framing (cost, risk, or customer impact) that matches the decision-maker's mandate.

## Production checklist
- [ ] Estimates to PM/PO always state a **range**, **2–3 key assumptions**, and a **date to resolve the main unknown**.
- [ ] Risk or tech-debt proposals open with **BLUF** (ask + date + business impact), not implementation jargon.
- [ ] Every "not now" includes a **trade, split, trigger, or workaround**.
- [ ] Rollback caveats (e.g., irreversible data writes) are stated explicitly before release.
