## TL;DR
Docker Compose wires multi-container apps together on one host using a single `compose.yaml`. Every service gets an entry in Compose's embedded **DNS**, explicit **networks** isolate traffic, **`depends_on` with `condition: service_healthy`** prevents race conditions at startup, and **profiles** keep optional tools out of your default stack.

## Intent
<Intent>
Understand how Docker Compose resolves service names over DNS, gates startup on real healthchecks, and separates configuration (`env_file`) from credentials (`secrets`) without needing Kubernetes.
</Intent>

## Problem
Running `docker run` by hand for a web server, database, and cache quickly breaks down: container IPs change on every restart, the web app crashes if it connects before Postgres finishes initializing, and passing passwords via `-e` exposes them in `docker inspect`.

## Solution
Compose reads a declarative `compose.yaml` and sets up three primitives automatically:

1. **Service DNS & networks:** Compose creates a project-scoped bridge network. Every container's `/etc/resolv.conf` points to Docker's embedded DNS server (`127.0.0.11`), which resolves service names (like `db`) to the active container IP. You can also split `frontend` and `backend` networks with `internal: true` so the database has no outbound internet route.
2. **Startup order with healthchecks:** Plain `depends_on: [db]` only waits for the container to start, not for the process inside to accept connections. Pairing `depends_on` with `condition: service_healthy` and a `healthcheck` ensures `web` starts only after `db` passes its readiness command (e.g., `pg_isready`).
3. **`env_file` vs `secrets`, plus `profiles`:** Use `env_file` for non-sensitive config (`NODE_ENV`, `PORT`), `secrets` to mount sensitive files at `/run/secrets/<name>`, and `profiles: ["debug"]` so admin UIs or seeders only run when requested (`docker compose --profile debug up`).

## Real-world analogy
<Analogy>
Think of Compose as a small office intercom system: you don't memorize anyone's extension IP—you dial "Accounting" (**service DNS**), the operator waits until the accountant unlocks their desk (**`service_healthy`**) before transferring callers, and sensitive keycards (**`secrets`**) stay in a locked folder rather than printed on everyone's name badge (**`env_file`**).
</Analogy>

## Code
A minimal, production-minded `compose.yaml` using `service_healthy`, isolated networks, `env_file`, `secrets`, and `profiles`:

```yaml
# compose.yaml (not run)
services:
  web:
    build: .
    ports:
      - "3000:3000"
    env_file:
      - .env.app
    secrets:
      - db_password
    networks:
      - frontend
      - backend
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    networks:
      - backend
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5
    volumes:
      - pgdata:/var/lib/postgresql/data

  adminer:
    image: adminer:4
    profiles: ["debug"]
    ports:
      - "8080:8080"
    networks:
      - backend

networks:
  frontend:
  backend:
    internal: true

volumes:
  pgdata:

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

## When you DON'T need this
- **Single-container apps or static sites:** If your app is one stateless binary or static assets (like this site), `docker run` or a static host is simpler than maintaining a `compose.yaml`.
- **Multi-node scheduling or auto-scaling:** Compose targets a single Docker Engine host. Once you need rolling updates across multiple machines, bin-packing, or self-healing across node failures, move to Kubernetes or a managed container platform.
- **Cost / complexity trade-off:** Compose is free and ships with Docker Desktop / Docker Engine, so its operational overhead is near zero—but single-host simplicity means zero built-in high availability if that host goes down.

## How to implement
<Steps>
  <Step>
    ### Define isolated networks
    Put `web` on `frontend` and `backend`, and put `db` only on `backend` with `internal: true`.
  </Step>
  <Step>
    ### Add a real healthcheck on dependencies
    Gate `web` with `depends_on.db.condition: service_healthy` so startup waits for readiness.
  </Step>
  <Step>
    ### Separate env_file from secrets
    Keep non-sensitive flags in `.env.app` and mount credentials via `secrets:` at `/run/secrets/`.
  </Step>
</Steps>
