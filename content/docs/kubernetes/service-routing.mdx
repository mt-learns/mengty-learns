## 1. Intent

<Intent>
Understand how Kubernetes decouples external traffic from ephemeral Pod IPs: **Ingress** handles Layer 7 HTTP routing, **Service** provides a stable virtual IP and load-balancing across endpoints, and **Pods** run the actual application containers.
</Intent>

## 2. Problem

Pods in Kubernetes are ephemeral—they get rescheduled, scaled up, or replaced during deployments, and each new Pod receives a new IP address. If clients or an external load balancer hardcoded Pod IPs, every rollout or crash would break traffic.

## 3. Solution

Kubernetes inserts two stable abstractions between external callers and Pods:

1. **Ingress** terminates TLS and inspects HTTP host/path rules (e.g. `shop.example.com/cart`), routing the request to the matching **Service** (`web`).
2. **Service** (`ClusterIP`) owns a stable virtual IP and DNS name (`web.default.svc.cluster.local`). An `EndpointSlice` continuously tracks only **Ready** Pods matching the Service's label selector (`app: web`), and `kube-proxy` (via iptables/IPVS/eBPF) distributes traffic to a healthy Pod.

## 4. Real-world analogy

<Analogy>
Think of **Ingress** as the building's front-desk directory ("Accounting is on Floor 3"), the **Service** as the department's shared phone extension (`ext. 300`), and **Pods** as the individual staff members answering that extension. Callers never need anyone's personal mobile number, and if someone goes on break (fails a readiness probe), the extension stops ringing their desk.
</Analogy>

## 7. Code

<Tabs items={['TypeScript (kubectl-style config)', 'YAML']}>
  <Tab value="TypeScript (kubectl-style config)">
```ts
// Declarative representation of a Service + Ingress routing pair
interface ServiceSpec {
  name: string;
  selector: Record<string, string>;
  port: number;
  targetPort: number;
}

interface IngressRule {
  host: string;
  path: string;
  serviceName: string;
  servicePort: number;
}

const webService: ServiceSpec = {
  name: 'web',
  selector: { app: 'web' },
  port: 80,
  targetPort: 8080,
};

const webIngress: IngressRule = {
  host: 'shop.example.com',
  path: '/cart',
  serviceName: webService.name,
  servicePort: webService.port,
};

console.log(
  `Route https://${webIngress.host}${webIngress.path} -> ${webIngress.serviceName}:${webIngress.servicePort} -> Pod:${webService.targetPort}`,
);
```
  </Tab>
  <Tab value="YAML">
```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
spec:
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /cart
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80
```

## 8. When to use / when to avoid

<Checklist
  use={[
    'You need HTTP/HTTPS host or path-based routing, TLS termination, or virtual hosting across multiple Services.',
    'You want a single external entry point instead of provisioning a cloud LoadBalancer per Service.',
    'Your backend Pods scale dynamically and need automatic endpoint discovery.',
  ]}
  avoid={[
    'You only need internal cluster-to-cluster communication (use a ClusterIP Service directly).',
    'You need non-HTTP TCP/UDP routing (consider Gateway API TCPRoute/UDPRoute or a LoadBalancer Service).',
    'You are starting a brand-new cluster that already standardizes on Kubernetes Gateway API.',
  ]}
/>

## 9. How to implement

<Steps>
  <Step>
    ### Label your Pods consistently
    Ensure your Deployment's `spec.template.metadata.labels` includes `app: web`.
  </Step>
  <Step>
    ### Create the ClusterIP Service
    Match `spec.selector` to `app: web`, expose `port: 80`, and forward to the container's `targetPort: 8080`.
  </Step>
  <Step>
    ### Configure readiness probes
    Add a `readinessProbe` on the Pod so unready Pods are excluded from the Service's `EndpointSlice`.
  </Step>
  <Step>
    ### Add the Ingress resource
    Define the `host` and `path` rule pointing `backend.service.name` to `web` on port `80`, then verify with `kubectl describe ingress web-ingress`.
  </Step>
</Steps>

## 12. Check yourself

<MyTake>
When a Service returns `502` or `503` behind an Ingress, my first command is always `kubectl get endpointslices -l kubernetes.io/service-name=web`. Nine times out of ten, either the label selector does not match the Pod labels or the Pod's readiness probe is failing.
</MyTake>
