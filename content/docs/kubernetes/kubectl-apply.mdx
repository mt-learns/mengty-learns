## TL;DR
`kubectl apply` does not talk to nodes or containers directly. It sends your YAML to **kube-apiserver**, which authenticates, authorizes, admits, and writes the desired state to **etcd**; controllers, **kube-scheduler**, **kubelet**, and the **CRI runtime** then asynchronously reconcile reality to match.

## Intent
<Intent>
Understand the asynchronous watch-and-reconcile loop behind `kubectl apply`, so you know where to look when a Deployment is stuck at `Pending`, `ImagePullBackOff`, or `0/1 Ready`.
</Intent>

## Problem
Many engineers assume `kubectl apply` is an imperative RPC that immediately starts containers and waits. When a Pod stays `Pending` or fails admission, guessing blindly wastes time because each stage—API validation, controller creation, scheduling, and node execution—is owned by a separate component.

## Solution
Kubernetes uses a **level-triggered reconciliation loop** centered on `kube-apiserver`:

1. **`kubectl` → API Server:** `kubectl apply` sends the manifest (or server-side apply patch) over HTTPS. The API Server runs **Authentication**, **Authorization (RBAC)**, and **Admission** (mutating then validating).
2. **API Server → `etcd`:** Once valid, the Deployment object is persisted in `etcd`.
3. **Controllers (`kube-controller-manager`):** Watching Deployments, the Deployment controller creates or updates a **ReplicaSet**, whose controller creates **Pod** objects (still unscheduled, `nodeName: ""`).
4. **Scheduler (`kube-scheduler`):** Watches unscheduled Pods, filters out nodes that lack CPU/memory or fail taints/affinities, scores the remaining nodes, and writes `spec.nodeName` via the API Server.
5. **`kubelet` → CRI Runtime:** Watching Pods bound to its node, `kubelet` calls the **Container Runtime Interface (CRI)** (e.g., `containerd`) to pull the image and start the container, then `kubelet` runs readiness probes and reports `Ready` status back to the API Server.

## Real-world analogy
<Analogy>
Think of a restaurant kitchen with a central order board (**API Server** + **etcd**). The waiter (**kubectl**) posts a ticket on the board. The kitchen lead (**Controller**) breaks a combo meal into individual dish tickets (**ReplicaSet → Pods**), the expediter (**Scheduler**) assigns each dish to a station (**Node**), and the station chef (**kubelet + CRI**) cooks it and marks it ready on the board.
</Analogy>

## Code
You can validate a Deployment manifest locally with `kubectl apply --dry-run=client` before sending it to a cluster:

```bash
# Client-side validation without mutating a cluster (not run against a live cluster)
kubectl apply -f deployment.yaml --dry-run=client -o yaml

# Apply and watch the reconciliation stages (not run against a live cluster)
kubectl apply -f deployment.yaml
kubectl get deployment,rs,pods -w
```

## When to use / when to avoid
<Checklist
  use={[
    'You want declarative, idempotent updates where Kubernetes converges cluster state to your YAML.',
    'You are debugging why a Pod is stuck in Pending (scheduler), ContainerCreating (kubelet/CRI), or rejected at apply time (API Server).',
  ]}
  avoid={[
    'You need imperative one-off debugging commands (use kubectl exec, logs, or port-forward instead of apply).',
    'You want Git to be the single source of truth instead of running kubectl apply from laptops (use GitOps).',
  ]}

## How to implement
<Steps>
  <Step>
    ### Author declarative manifests
    Define `Deployment` manifests with resource requests/limits and readiness probes.
  </Step>
  <Step>
    ### Validate before applying
    Run `kubectl apply --dry-run=client` or `kubeconform` in CI to catch schema errors early.
  </Step>
  <Step>
    ### Apply and inspect events
    Run `kubectl apply -f ...` and check `kubectl describe pod <name>` if scheduling or image pull stalls.
  </Step>
</Steps>

## Pros / Cons
<ProsCons
  pros={[

  ]}
  cons={[
    'kubectl apply returning 0 only means etcd accepted the desired state, not that Pods are Ready.',
