## TL;DR
**Readiness** controls *traffic* (failure removes the Pod from `EndpointSlices` without restarting it), **liveness** controls *restarts* (failure kills a deadlocked container), and **startup** protects *slow boots* by delaying liveness and readiness until the first success.

## Intent
<Intent>
Separate traffic-gating (`readinessProbe`) from process-restarting (`livenessProbe`) and slow-boot protection (`startupProbe`) so you don't trigger restart loops or cascading outages.
</Intent>

## Problem
Without probes, Kubernetes assumes a Pod is ready the millisecond its container process starts—sending user traffic to an app that is still warming caches or loading config. Conversely, putting a heavy database check inside `livenessProbe` causes kubelet to restart every Pod in the fleet whenever the database has a 5-second hiccup.

## Solution
| Probe | Failure action | Use it for |
|---|---|---|
| **`readinessProbe`** | Sets `Ready=False`; removes Pod IP from `EndpointSlice` | Temporary inability to serve traffic (warming up, draining, overloaded) |
| **`livenessProbe`** | Kills and restarts the container | Unrecoverable deadlocks where only a restart fixes the process |
| **`startupProbe`** | Delays liveness & readiness; kills container if `failureThreshold` expires | Legacy/heavy apps that take 30–120s to boot |

## Real-world analogy
<Analogy>
A **startupProbe** is waiting for a chef to finish preheating the oven before opening; a **readinessProbe** is flipping the door sign to "Be right back" when the kitchen is temporarily backed up; and a **livenessProbe** is calling the manager to restart the shift because the kitchen has completely frozen.
</Analogy>

## Code
Minimal Deployment probe configuration for an HTTP service (such as `labs/docker-multistage-next` serving `/healthz`):

```yaml
# Partial Pod container spec (not run against a cluster)
containers:
  - name: web
    image: ghcr.io/example/web:1.0.0
    ports:
      - containerPort: 3000
    startupProbe:
      httpGet:
        path: /healthz
        port: 3000
      failureThreshold: 12
      periodSeconds: 5
    readinessProbe:
      httpGet:
        path: /readyz
        port: 3000
      periodSeconds: 5
      failureThreshold: 2
    livenessProbe:
      httpGet:
        path: /healthz
        port: 3000
      periodSeconds: 15
      failureThreshold: 3
```

## When you DON'T need this
- **Non-Kubernetes platforms:** Static sites on Cloudflare Workers/Pages, Docker Compose (`HEALTHCHECK`), or serverless functions don't use Kubernetes probes or `EndpointSlices`.
- **Kubernetes `Job` / `CronJob` batch Pods:** Batch jobs run to completion and exit; they don't serve Service traffic and shouldn't have `readinessProbe` or `livenessProbe`.
- **Cost / complexity trade-off:** Probes cost almost nothing in CPU (a lightweight `/healthz` handler returning `200 OK` takes microseconds), but poorly tuned timeouts (`timeoutSeconds: 1` on a GC-pausing app) or DB-coupled liveness probes can cause self-inflicted outages. Keep `/healthz` cheap and local to the process.

## How to implement
<Steps>
  <Step>
    ### Expose cheap local health endpoints
    Have `/healthz` verify the process event loop is alive (no external DB calls) and `/readyz` verify local initialization is complete.
  </Step>
  <Step>
    ### Configure `readinessProbe` first
    Set `periodSeconds` and `failureThreshold` so rolling updates only shift traffic once new Pods are ready.
  </Step>
  <Step>
    ### Add `startupProbe` for slow starters
    Use `startupProbe` instead of a huge `initialDelaySeconds` on `livenessProbe` so fast boots become ready immediately while slow boots aren't killed.
  </Step>
</Steps>
