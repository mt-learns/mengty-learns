## TL;DR
Both **Argo CD** and **Flux** are graduated CNCF GitOps pull controllers. Pick **Argo CD** if you want a **built-in web UI, SSO, and visual resource diffing** for app teams; pick **Flux** if you prefer **lightweight modular CRDs, native Helm release lifecycle, and Kubernetes-native RBAC** with no UI overhead.

## Context
Once you adopt pull-based GitOps (`gitops/what-is-gitops`), you need an in-cluster controller to watch Git and reconcile Kubernetes manifests. Argo CD and Flux are the two standard choices, and migrating later is non-trivial because their CRDs (`Application`/`ApplicationSet` vs `GitRepository`/`Kustomization`/`HelmRelease`) differ.

## Comparison

| Dimension | Argo CD (v3.6) | Flux CD (v2.10) |
|---|---|---|
| **Architecture** | Monolithic control plane (API server, repo-server, application-controller) | Composable GitOps Toolkit controllers (`source`, `kustomize`, `helm`, `notification`) |
| **Web UI** | Rich built-in UI (resource tree, live diff, sync buttons, logs) | None built-in (CLI `flux`, or optional third-party/Headlamp plugins) |
| **Multi-tenancy** | `AppProject` + built-in RBAC + OIDC/SSO | Native Kubernetes `ServiceAccount` + `Namespace` RBAC |
| **Helm support** | Renders via `helm template` and tracks manifests directly | `helm-controller` executes real Helm releases (`HelmRelease` CRD) |
| **Kustomize support** | Built-in via repo-server | Dedicated `kustomize-controller` with health checks & dependencies |
| **Footprint** | Heavier (Redis + API server + repo-server + controller) | Lighter; install only the controllers you need |

## Decision criteria
1. **Do developers need a self-service UI?** If non-k8s-expert developers debug deploys via a browser, Argo CD's UI saves hours of `kubectl` support.
2. **Do you rely heavily on Helm hooks, tests, and native Helm releases?** Flux's `helm-controller` runs real Helm SDK upgrades/rollbacks rather than `helm template` + `kubectl apply`.
3. **How do you model multi-tenancy?** Argo CD manages its own `AppProject` RBAC layer; Flux delegates directly to Kubernetes `ServiceAccount` impersonation per namespace.

<MyTake>
For most product teams starting with GitOps, I pick **Argo CD** because the visual resource tree and live diff immediately answer "why is my deploy stuck?" without giving everyone `kubectl` access. For platform-heavy clusters running dozens of Helm operators, **Flux** is cleaner and lighter.
</MyTake>

## Gotchas
- **Argo CD Helm hooks:** because Argo CD uses `helm template`, Helm lifecycle hooks are mapped to Argo CD sync waves/hooks—some complex third-party charts behave slightly differently than `helm upgrade`.
- **Flux `Kustomization` vs Kustomize:** Flux's `Kustomization` CRD wraps Kustomize *and* plain YAML directories, which confuses newcomers expecting a `kustomization.yaml` requirement.
- **Secret decryption:** neither tool decrypts secrets magically—both require a plugin or controller (ESO, SOPS, or SealedSecrets).

## Production checklist
- [ ] Pin controller versions in your bootstrap repo
- [ ] Enable automated drift detection and alerts (Slack/webhook) for failed syncs
- [ ] Scope tenant permissions (`AppProject` in Argo CD; `spec.serviceAccountName` in Flux) so one team cannot deploy into another team's namespace
- [ ] Store Git credentials with read-only deploy keys or GitHub App tokens
