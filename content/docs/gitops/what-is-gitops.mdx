## TL;DR
**GitOps** makes a declarative **Git repository** the single source of truth for infrastructure and apps. Instead of CI pushing `kubectl apply` with cluster-admin keys, an in-cluster **pull agent** (Argo CD or Flux) watches Git and continuously converges the cluster to match.

## Intent
<Intent>
Understand the four OpenGitOps principles and why pull-based reconciliation beats ad-hoc `kubectl apply` scripts from CI runners.
</Intent>

## Problem
In traditional **push-based CD**, your CI pipeline builds an image, logs into the cluster with a `kubeconfig` secret, and runs `kubectl apply` or `helm upgrade`. That creates two risks: CI holds powerful cluster credentials, and once the CI job finishes, nobody notices if someone manually edits the cluster later.

## Solution
The **OpenGitOps** standard defines four principles:

1. **Declarative:** The desired state of the system is expressed declaratively (Kubernetes YAML, Helm values, Kustomize).
2. **Versioned and Immutable:** Desired state is stored in Git with full commit history, PR reviews, and `git revert` rollbacks.
3. **Pulled Automatically:** Software agents inside the cluster (Argo CD or Flux) automatically pull desired state declarations from Git.
4. **Continuously Reconciled:** Agents observe actual cluster state and continuously apply changes whenever actual state diverges from Git.

## Real-world analogy
<Analogy>
Think of a thermostat (**GitOps agent**) mounted inside your living room (**cluster**). You set the target temperature on the wall dial (**Git commit**). The thermostat continuously measures the room and turns the heater on or off until the room matches the dial—even if someone briefly opens a window.
</Analogy>

## Code
An Argo CD `Application` manifest declaring which Git repo and path to reconcile into the cluster:

```yaml
# Declarative Argo CD Application (not run — requires Argo CD installed in cluster)
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/example/k8s-config.git
    targetRevision: main
    path: apps/web
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

## When to use / when to avoid
<Checklist
  use={[
    'You run Kubernetes clusters and want auditable, PR-reviewed deployments with easy git revert rollbacks.',
    'You want to remove cluster-admin kubeconfig secrets from external CI runners.',
  ]}
  avoid={[
    'You are deploying a single static site to a managed host (a simple CI deploy step is lighter than running Argo CD or Flux).',
    'Your team still relies on imperative hotfixes via kubectl edit without committing back to Git.',
  ]}

## How to implement
<Steps>
  <Step>
    ### Separate app code and config (or use a dedicated config path)
    Keep declarative Kubernetes manifests in a tracked Git branch.
  </Step>
  <Step>
    ### Install Argo CD or Flux in the cluster
    Grant the in-cluster controller read-only access (deploy key or GitHub App) to your config repo.
  </Step>
  <Step>
    ### Point an Application or Kustomization at the repo
    Enable automated sync and `selfHeal` once your manifests are tested in CI.
  </Step>
</Steps>

## Pros / Cons
<ProsCons
  pros={[
    'Least privilege: CI never needs direct write credentials to production Kubernetes.',

  cons={[
