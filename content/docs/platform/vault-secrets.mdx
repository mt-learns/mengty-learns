## Intent

<Intent>
Understand how Vault acts as an **identity broker with a cryptographic barrier**: workloads trade platform identities (Kubernetes ServiceAccounts, OIDC JWTs, AppRoles) for short-lived tokens and **leased dynamic credentials** instead of static shared passwords.
</Intent>

## Problem

Static database passwords stored in `.env` files, CI variables, or Kubernetes `Secrets` are shared across replicas, rarely rotated, and painful to revoke after a leak because you cannot tell which workload is using which copy.

## Solution

Vault separates **authentication** (who you are), **authorization** (HCL policies on `method + path`), and **secret engines**:

1. **Authenticate to get a token:** A workload proves its identity via Kubernetes auth, AppRole, or OIDC/JWT and receives a scoped Vault token.
2. **Issue dynamic, leased credentials:** Instead of reading a shared password from KV, Vault's Database, PKI, or Cloud engines generate a unique credential on demand and attach a `lease_id` with a `ttl` and `max_ttl`.
3. **Renew or revoke:** Vault Agent (or the External Secrets Operator) renews leases in the background and re-authenticates before `max_ttl`. During an incident, `vault lease revoke -prefix database/creds/app` drops every active credential for that role immediately.

## Real-world analogy

<Analogy>
Instead of giving every contractor a copy of the building's master brass key (**static password**), the front desk checks their company badge (**platform auth**) and prints a temporary keycard (**leased credential**) that opens only one room and expires automatically at 5 PM—or can be deactivated in one click if lost.
</Analogy>

## Structure

Essential Vault CLI commands for daily operations:

```bash
# Authenticate and inspect token capabilities (not run)
vault login -method=oidc
vault token lookup
vault token capabilities kv/data/app/config

# Dynamic database credentials & emergency revocation (not run)
vault read database/creds/app-ro
vault lease revoke -prefix database/creds/app-ro

# Raft HA snapshot backup (not run)
vault operator raft list-peers
vault operator raft snapshot save snap-$(date +%F).snap
```

## When to use / when to avoid

- **Use Vault** when you run multi-environment or regulated infrastructure needing dynamic database/PKI credentials, Transit encryption-as-a-service, and a unified audit log.
- **Avoid self-hosting Vault HA** for a tiny single-cloud app where your cloud provider's managed Secrets Manager + IAM/OIDC roles already cover your needs without Raft/unseal ops.

## Pros / Cons

- **Pros:** Eliminates static shared credentials; instant prefix revocation; built-in audit trail and Transit encryption.
- **Cons:** Tier-0 dependency (if Vault is sealed or down, new leases fail); requires KMS/HSM auto-unseal, Raft snapshot drills, and dual audit devices so a full disk does not halt the cluster.
