## TL;DR
**Network reachability is not authorization.** Use a VPN (WireGuard or IKEv2) to shrink who can *attempt* a connection, then enforce **OIDC + group claims** at the internal gateway and **short-lived SSH certs** on bastions. Always configure **split-horizon DNS** and keep an **out-of-band** admin path so a bad VPN change never locks you out.

## Why it exists
A classic flat-network VPN lets any connected laptop reach every internal dashboard, database, and Kubernetes API. Zero-trust private access treats the VPN as network hygiene only: per-device keys tied to your IdP lifecycle, split-tunnel routes, and per-app authentication.

## Mental model

1. **Access layers:**
   - **Internal web apps:** VPN (split tunnel) → Internal Ingress/Gateway + **OIDC group check** → `NetworkPolicy`.
   - **Host/break-glass admin:** Hardware-backed SSH key or short-lived **Vault SSH certificate** → `ProxyJump` bastion with MFA and session recording.
   - **Kubernetes API:** Private API endpoint reachable over VPN + `kubectl` OIDC login (never a static admin token in `~/.kube/config`).
2. **WireGuard `AllowedIPs`:** On the server, `AllowedIPs = 10.90.4.17/32` restricts which IP that peer may spoof. On the client, `AllowedIPs = 10.30.0.0/16` enables **split tunneling** so personal internet traffic stays off the corporate concentrator (use `0.0.0.0/0` only when policy mandates full-tunnel DLP inspection).
3. **Split-horizon DNS:** Push internal resolvers over the tunnel and route only your internal domain suffix (e.g. `~internal.example`) so internal names never leak into public DNS or Certificate Transparency logs.

## Do it

Inspect WireGuard handshakes, split-DNS resolution, and MTU on Linux:

```bash
# Check active WireGuard peers and last handshake age (not run)
wg show wg0 latest-handshakes

# Verify split-horizon DNS uses the internal resolver (not run)
resolvectl status
dig api.internal.example @10.30.0.10

# Test Path MTU if small requests succeed but large payloads hang (not run)
ping -M do -s 1392 10.30.10.20
```

Connect to private hosts cleanly via `ProxyJump` without agent forwarding:

```text
# ~/.ssh/config (not run)
Host bastion
  HostName bastion.mgmt.example
  User ops
  IdentityFile ~/.ssh/id_ed25519_sk

Host 10.30.*
  ProxyJump bastion
  StrictHostKeyChecking yes
```

## Gotchas
- **PMTU / MTU black holes:** Tunnel headers reduce effective MTU; if small health checks work but TLS handshakes or large responses hang, set WireGuard `MTU = 1420` (or `1280`) and clamp TCP MSS.
- **Overlapping RFC1918 CIDRs:** Home routers (`192.168.1.0/24`) colliding with office/VPC subnets silently break routing—plan non-overlapping internal CIDRs (`10.x.0.0/16`) early.
- **Public wildcards for internal names:** Issuing a public Let's Encrypt cert for `*.internal.example` publishes your internal hostnames to public Certificate Transparency logs; use an internal CA (Vault PKI) instead.
- **No out-of-band rollback:** Never manage the VPN concentrator *only* through the VPN tunnel itself.

## Production checklist
- [ ] Every private app enforces OIDC + group entitlement at the gateway (reachability alone is never enough).
- [ ] One VPN key/certificate per **device**, tied to IdP offboarding (short TTL).
- [ ] Split-horizon DNS resolves internal zones internally without publishing them to public DNS.
- [ ] Bastion uses `ProxyJump` (no SSH agent forwarding), MFA, and session recording.
- [ ] Automated check verifies internal LoadBalancers retain RFC1918 private IPs after chart upgrades.
