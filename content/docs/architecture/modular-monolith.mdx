## TL;DR
A **Modular Monolith** runs as **one deployable process** but enforces **strict module boundaries**: each business module (`orders`, `inventory`, `billing`) owns its own internal code and database tables, and modules talk **only through explicit public APIs** or in-process events.

## Intent
<Intent>
Get the clean domain boundaries of microservices without paying the operational tax of network calls, distributed tracing, and multi-repo deployments.
</Intent>

## Problem
In an unmodularized monolith, `BillingService` imports `orders/internal/order-model` and joins directly against `orders_items` in SQL. Over time, every module depends on every other module's internals—turning simple schema changes into risky whole-app rewrites.

## Solution
A Modular Monolith applies two hard rules inside a single repository and deployment:

1. **Private internals, public `index.ts` API:** `src/modules/inventory/index.ts` exports `InventoryApi` (`reserveStock()`). No other module may import from `src/modules/inventory/internal/*`.
2. **No shared tables:** `orders` owns `orders.*` tables (separate PostgreSQL schema or prefixed tables with no foreign keys across modules). If `orders` needs stock availability, it calls `InventoryApi`—never `SELECT * FROM inventory_items`.

Because everything runs in one process, `InventoryApi` is a fast TypeScript method call today—and if `inventory` ever needs to scale independently later, extracting it to a network service only requires swapping the `InventoryApi` adapter.

## Real-world analogy
<Analogy>
Think of **watertight compartments** inside a ship hull. All compartments sail together as one vessel (one deployment), but each compartment has sealed bulkheads and communicates through designated hatches (public APIs), so a leak in one doesn't flood the rest.
</Analogy>

## Code
Enforcing module boundaries with explicit `index.ts` exports and DTO contracts:

```ts
// src/modules/inventory/index.ts (Public API — the ONLY file other modules may import)
export interface ReserveStockResult {
  reserved: boolean;
  remaining: number;
}

export interface InventoryApi {
  reserveStock(sku: string, qty: number): Promise<ReserveStockResult>;
}

// src/modules/orders/place-order.ts (Consumes InventoryApi, never inventory/internal/*)
export class PlaceOrder {
  constructor(private readonly inventory: InventoryApi) {}

  async execute(sku: string, qty: number): Promise<void> {
    const res = await this.inventory.reserveStock(sku, qty);
    if (!res.reserved) throw new Error('Out of stock');
  }
}
```

## When to use / when to avoid
<Checklist
  use={[

  ]}
  avoid={[
    'Different modules have radically different scaling or runtime needs (e.g., Python ML inference vs Node.js web API).',

## How to implement
<Steps>
  <Step>
    ### Split `src/modules/<domain>/`
    Group code by business capability (`orders/`, `inventory/`), not technical layer (`controllers/`, `services/`).
  </Step>
  <Step>
    ### Add lint/compiler boundary checks
    Configure ESLint `no-restricted-imports` or `eslint-plugin-boundaries` so deep imports into `modules/*/internal/**` fail CI.
  </Step>
  <Step>
    ### Separate database schemas
    Use separate Postgres schemas (`orders.*`, `inventory.*`) or distinct DB users in CI to catch accidental cross-module SQL joins.
  </Step>
</Steps>
