## TL;DR
Treat database schema changes as **backward-compatible steps**, never single-deploy swaps. Use **versioned migrations**, apply **expand/contract** so old and new app code coexist during rollouts, **backfill in small batches**, **never edit an applied migration**, and plan for **forward-only fixes** instead of destructive rollbacks.

## Why it exists
During a rolling deploy, old pods and new pods share the same database for seconds or minutes. If a migration renames or drops a column before old pods drain, live requests crash with `column does not exist`—and rolling back the app code won't restore dropped data.

## Mental model
Always keep the database compatible with **both** the previous release (`N-1`) and the next release (`N`) until `N-1` is completely gone.

## Do it

### 1. Versioned migrations (immutable history)
Store every DDL change as a timestamped or sequential file (`0001_init.sql`, `0002_add_user_handle.sql`) tracked in a `_migrations` table. Once a migration is merged and applied to any shared environment, **never edit it**—create a new forward migration (`0003_...`) to fix mistakes.

### 2. Expand / contract for zero downtime
Suppose you want to rename `users.full_name` to `users.display_name`:

```sql
-- Deploy 1 (Expand): safe alongside old app code (not run)
ALTER TABLE users ADD COLUMN display_name TEXT;

-- Deploy 2 (Backfill in small batches, e.g., 1,000 rows per tx, not run)
UPDATE users
SET display_name = full_name
WHERE id IN (
  SELECT id FROM users
  WHERE display_name IS NULL AND full_name IS NOT NULL
  LIMIT 1000
);

-- Deploy 3 (Enforce without long table lock, Postgres 12+, not run)
ALTER TABLE users ADD CONSTRAINT chk_display_name_nn
  CHECK (display_name IS NOT NULL) NOT VALID;
ALTER TABLE users VALIDATE CONSTRAINT chk_display_name_nn;

-- Deploy 4 (Contract, only after old app instances are gone, not run)
ALTER TABLE users DROP COLUMN full_name;
```

### 3. Rollback reality
As covered in [Deployment & Rollback Strategies](/docs/ci-cd/deploy-and-rollback), rolling back application containers is fast, but **rolling back a database migration is often unsafe**:
- If Deploy 1 only **added** a nullable column or `CONCURRENTLY` index, you can roll back the app code without touching the DB at all.
- Never run `down.sql` scripts that `DROP TABLE` or `DROP COLUMN` in production—you will destroy data written after the deploy. Fix forward with a new migration instead.

### 4. Liquibase & regulated environments
In enterprise and regulated systems (SOC 2, PCI DSS, banking), schema migrations also serve as **audit evidence**:
- **Separate DDL vs DML roles:** Run migrations with a dedicated `migrator` role that owns DDL, while the runtime application user has only `SELECT`/`INSERT`/`UPDATE`/`DELETE` (DML)—never `ALTER` or `DROP` in production.
- **SQL-first Liquibase changelogs:** Prefer formatted SQL or YAML changelogs with explicit `rollback` blocks and `runInTransaction:false` for `CREATE INDEX CONCURRENTLY`.
- **Compatibility window ≥ rollback horizon:** Keep the old column alive for at least one full release cycle (and any reconciliation window) before running the Contract `DROP COLUMN` deploy.
- **Dry-run + evidence:** Rehearse migrations against a masked production-sized snapshot, record `lock_timeout` / duration / row counts, and test rollback + re-apply in CI.

```sql
-- liquibase formatted sql
-- changeset team:2026-11-27-add-display-name runInTransaction:false
SET lock_timeout = '2s';
ALTER TABLE users ADD COLUMN display_name TEXT;
-- rollback ALTER TABLE users DROP COLUMN IF EXISTS display_name;
```

## When you DON'T need this
- **Pre-launch prototypes with zero real users:** When you can afford a 5-second maintenance window or `db push`, multi-deploy expand/contract is unnecessary ceremony.
- **Static sites with no database:** This site has no runtime database and ships only static assets.
- **Cost / complexity trade-off:** Expand/contract splits one conceptual rename into 2–4 smaller PRs and deploys. In return, you get zero-downtime rollouts and painless code rollbacks.

## Gotchas
- **`lock_timeout` omitted on `ALTER TABLE`:** Even fast metadata-only `ALTER TABLE` commands queue behind a long-running `SELECT` and block every subsequent query until you set `SET lock_timeout = '2s';`.
- **`CREATE INDEX` without `CONCURRENTLY`:** Standard `CREATE INDEX` blocks all writes on the table for the entire build duration.
- **Single-transaction backfills:** Updating 5 million rows in one `UPDATE` holds row locks, bloats WAL, and can stall replicas.

## Production checklist
- [ ] Migrations run with a dedicated `lock_timeout` (e.g., `2s`) and `statement_timeout`.
- [ ] New indexes use `CREATE INDEX CONCURRENTLY` (outside a transaction block).
- [ ] Backfills run in bounded batches (500–5,000 rows) with short pauses between batches.
- [ ] Destructive drops (`DROP COLUMN`, `DROP TABLE`) happen only in a separate follow-up deploy after old code is retired.
- [ ] Applied migration files are treated as append-only and never edited.
