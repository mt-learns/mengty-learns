## TL;DR
**Clean Architecture** divides software into four concentric circles—**Entities**, **Use Cases**, **Interface Adapters**, and **Frameworks & Drivers**—governed by one strict **Dependency Rule**: source-code dependencies point only inward, and outer-ring calls cross boundaries via Input/Output Port interfaces.

## Intent
<Intent>
Make your system independent of frameworks, UI, and databases by isolating enterprise rules (Entities) and application workflows (Use Cases) behind explicit Input/Output boundaries.
</Intent>

## Problem
When controllers pass framework `Request` objects straight into business logic, or business logic returns ORM entities straight to HTTP responses, every layer becomes coupled to the web framework and database schema. Testing a single use case requires mocking HTTP and SQL.

## Solution
Clean Architecture organizes components into four rings and solves the "crossing boundaries" problem with Dependency Inversion:

1. **Entities:** Enterprise-wide business objects and rules (`Order.create(...)`).
2. **Use Cases (Interactors):** Application-specific workflows (`PlaceOrderInteractor`) that orchestrate Entities and declare **Input/Output Ports** (`PlaceOrderInputPort`, `OrderGateway`, `OrderPresenter`).
3. **Interface Adapters:** Convert data between Use Case models and external formats—**Controllers** call Input Ports, **Presenters** implement Output Ports to format ViewModels, and **Gateways** implement persistence ports.
4. **Frameworks & Drivers:** Web servers, SQL databases, and CLI runners—treated as replaceable plugins at the edge.

## Real-world analogy
<Analogy>
Think of a hospital surgery team: the **Use Case Interactor** is the lead surgeon following a strict protocol, **Entities** are the patient's vital rules, **Gateways/Presenters** are the standardized instrument trays and monitors, and **Frameworks & Drivers** are the specific brand of hospital bed or lighting—swappable without rewriting the surgical procedure.
</Analogy>

## Code
Using the shared **Order** service in TypeScript with explicit Interactor, Gateway, and Presenter boundaries:

<Tabs items={['TypeScript']}>
  <Tab value="TypeScript">
```ts
// --- Entities (src/entities/order.ts) ---
export interface OrderItem {
  sku: string;
  priceCents: number;
  qty: number;
}

export class Order {
  constructor(
    public readonly id: string,
    public readonly customerId: string,
    public readonly totalCents: number,
  ) {}

  static create(customerId: string, items: OrderItem[]): Order {
    if (items.length === 0) throw new Error('Empty order');
    const totalCents = items.reduce((sum, i) => sum + i.priceCents * i.qty, 0);
    return new Order(crypto.randomUUID(), customerId, totalCents);
  }
}

// --- Use Cases & Ports (src/use-cases/place-order.ts) ---
export interface PlaceOrderRequest {
  customerId: string;
  items: OrderItem[];
}

export interface PlaceOrderResponse {
  orderId: string;
  totalCents: number;
}

export interface OrderGateway {
  save(order: Order): Promise<Order>;
}

export interface OrderPresenter {
  present(res: PlaceOrderResponse): void;
}

export class PlaceOrderInteractor {
  constructor(
    private readonly gateway: OrderGateway,
    private readonly presenter: OrderPresenter,
  ) {}

  async execute(req: PlaceOrderRequest): Promise<void> {
    const order = Order.create(req.customerId, req.items);
    const saved = await this.gateway.save(order);
    this.presenter.present({ orderId: saved.id, totalCents: saved.totalCents });
  }
}
```

## When to use / when to avoid
<Checklist
  use={[
    'You are building a long-lived product with complex use cases that must remain testable without web or DB frameworks.',
    'Multiple delivery mechanisms (REST API, CLI, background jobs) share the same Use Case Interactors.',
  ]}
  avoid={[
    'Simple CRUD microservices where Presenter + Input/Output Port interfaces just add ceremony.',
    'Early-stage prototypes where speed of iteration matters more than strict boundary isolation.',
  ]}
/>

## How to implement
<Steps>
  <Step>
    ### Write Entities and Use Case Interactors first
    Keep `Order` and `PlaceOrderInteractor` free of framework or database imports.
  </Step>
  <Step>
    ### Define Gateway and Presenter interfaces in Use Cases
    Let the Interactor own the contracts it needs; outer rings implement them.
  </Step>
  <Step>
    ### Pass plain DTOs across boundaries
    Map HTTP payloads to `PlaceOrderRequest` in the Controller and `PlaceOrderResponse` to HTTP JSON in the Presenter.
  </Step>
</Steps>

## Pros / Cons
