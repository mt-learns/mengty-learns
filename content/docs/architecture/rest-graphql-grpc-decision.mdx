## TL;DR
Don't pick one API style for everything—draw **boundaries**. Use **REST + OpenAPI** for public/partner APIs and simple CRUD, **GraphQL** (or a **REST BFF**) when a frontend aggregates 3+ backends, and **gRPC + Protobuf** for internal high-throughput service-to-service calls.

## Why it exists
Boards often mandate "GraphQL everywhere" or "gRPC everywhere" in the name of consistency. Partners then demand OpenAPI specs anyway, internal services pay JSON/field-selection overhead they don't need, and audit logs turn into opaque `POST /graphql 200` lines.

## Comparison table

| Dimension | REST + OpenAPI | GraphQL | gRPC + Protobuf |
|---|---|---|---|
| **HTTP / CDN caching** | Native (`GET`, `ETag`, `304`) | Needs persisted queries over `GET` | None at HTTP layer |
| **Browser native** | Yes | Yes | No (needs gRPC-Web proxy) |
| **Contract enforcement** | OpenAPI spec + diff/contract tests | Executable schema | Compiled `.proto` + `buf breaking` |
| **Observability** | Route + method + status out of the box | Requires operation-name tagging | Structured method + rich status codes |
| **Streaming** | SSE / WebSockets | Subscriptions | Native bidirectional HTTP/2 |
| **Best boundary** | Public, partner, standard CRUD | Multi-backend UI aggregation | Internal service mesh |

## Gotchas
- **Using gRPC for browser clients directly:** You end up running an Envoy proxy and losing standard DevTools inspection; expose a REST BFF at the edge instead.
- **Using GraphQL between internal microservices:** Backend callers usually want a fixed payload with deadline propagation, not dynamic field selection.
- **Small teams splitting into 3 toolchains prematurely:** For a small team with 2–3 services, **REST + OpenAPI everywhere** is a completely respectable, low-overhead default.

## Production checklist
- [ ] Keep REST + OpenAPI as the default for partner/public APIs and simple services.
- [ ] Gate contract changes per boundary in CI (`openapi-diff`, `graphql-inspector`, `buf breaking`).
- [ ] Add a BFF or GraphQL layer only when frontend waterfalls across multiple backends are measurably hurting UX.
