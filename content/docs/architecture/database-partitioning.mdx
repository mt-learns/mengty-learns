## TL;DR
**Table partitioning** splits one logical table into smaller physical tables by **Range**, **List**, or **Hash**. Its value comes from **partition pruning** (skipping irrelevant chunks at query time) and **instant archival** (`DETACH`/`DROP` instead of massive `DELETE`s)—never use it as a substitute for indexing.

## 1. Intent

<Intent>
Keep multi-hundred-gigabyte tables fast to query, vacuum, and archive by dividing them along a natural boundary that matches your dominant query predicate.
</Intent>

## 2. Problem

An unpartitioned `audit_events` table grows to 2 billion rows. Two things break at once:
1. **Archival:** Deleting rows older than 2 years with `DELETE FROM audit_events WHERE created_at < ...` generates tens of gigabytes of WAL, spikes replication lag, and leaves millions of dead tuples for `autovacuum`.
2. **Maintenance:** `REINDEX` or `VACUUM` on the whole table takes hours, and monthly reports scan a giant 80 GB index that evicts hot working data from the buffer cache.

## 3. Solution

Declare a partitioned parent table (`PARTITION BY RANGE (created_at)`) with monthly child partitions:

| Strategy | Partition key | Best fit |
|---|---|---|
| **Range** | `created_at` (month/day) | Time-series logs, events, orders with retention policies |
| **List** | `region_code` / `tenant_tier` | Discrete domains, regional data residency, per-entity backups |
| **Hash** | `account_id` | Uniform write/index distribution when no time/region boundary exists (no `DROP` archival) |

When a query filters on `created_at >= '2026-07-01' AND created_at < '2026-08-01'`, the planner **prunes** every other partition before touching disk.

## 4. Real-world analogy

<Analogy>
Think of **monthly bank statements filed in separate physical binders**. To audit July, you pull only the July binder off the shelf instead of flipping through seven years of paper. When year-one binders expire, you shred the entire binder in seconds instead of erasing individual lines with correction tape.
</Analogy>

## 7. Code

```sql
-- 1. Parent table: composite primary key includes partition key (created_at)
CREATE TABLE audit_events (
    id          BIGINT GENERATED ALWAYS AS IDENTITY,
    created_at  TIMESTAMPTZ NOT NULL,
    actor_id    TEXT NOT NULL,
    action      TEXT NOT NULL,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- 2. Monthly partitions + local index template
CREATE TABLE audit_events_2026_07 PARTITION OF audit_events
    FOR VALUES FROM ('2026-07-01 00:00:00+00') TO ('2026-08-01 00:00:00+00');

CREATE INDEX idx_audit_events_actor ON audit_events (actor_id, created_at);

-- 3. Pruning works: bare partition key compared to bounds
EXPLAIN (ANALYZE)
SELECT * FROM audit_events
WHERE created_at >= '2026-07-01' AND created_at < '2026-08-01'
  AND actor_id = 'svc-deploy';

-- 4. Instant archival (metadata operation, no massive DELETE)
ALTER TABLE audit_events DETACH PARTITION audit_events_2024_01 CONCURRENTLY;
```

## 8. When to use / when to avoid

<Checklist
  use={[
    "Tables exceeding ~100 GB or hundreds of millions of rows with clear time-series or tenant boundaries.",
    "Compliance retention policies where dropping old months must not saturate WAL or autovacuum.",
    "Hot working sets where only the latest 1–3 partitions need to stay warm in shared_buffers.",
  ]}
  avoid={[
    "Small or medium tables where B-tree and partial indexes already give sub-10ms queries.",
    "Using partitioning to avoid creating proper indexes—a pruned partition still needs indexes inside it.",
  ]}
/>

## 9. How to implement

<Steps>
  <Step>
    ### Pick the partition key from your dominant query
    Ensure most hot queries include the partition key without wrapping it in functions like `date_trunc()`.
  </Step>
  <Step>
    ### Include the partition key in unique constraints
    Update primary keys and `UNIQUE` indexes to `(id, partition_key)` because PostgreSQL indexes are local.
  </Step>
  <Step>
    ### Automate future partition creation
    Pre-create partitions 2–3 months ahead via a scheduled job and alert if next month's partition is missing.
  </Step>
  <Step>
    ### Detach expired partitions concurrently
    Use `DETACH PARTITION ... CONCURRENTLY` (PostgreSQL 14+) before archiving or dropping old data.
  </Step>
</Steps>
