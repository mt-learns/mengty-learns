## TL;DR
**Events** (`OrderPlaced`) decouple producers from consumers, unlike **Commands** (`ChargeCard`). Never update your database and publish to Kafka/RabbitMQ in two separate calls (**dual-write bug**)—write the event to an **`outbox` table inside the same DB transaction**, and let a relay publish it with at-least-once delivery.

## Intent
<Intent>
Guarantee that every committed state change in your database reliably produces its corresponding domain event—with zero lost events and zero phantom events on rollback.
</Intent>

## Problem
Consider the naive dual-write:
1. `await db.orders.insert(order)` succeeds.
2. `await broker.publish('OrderPlaced', ...)` times out or the pod crashes.

Now the order exists in Postgres, but Inventory and Billing never hear about it. Wrapping it the other way (`publish` before `COMMIT`) is worse: if the transaction rolls back, consumers react to an order that doesn't exist.

## Solution
The **Transactional Outbox** uses your database's own ACID transaction as the bridge:

1. **Single ACID transaction:** inside `BEGIN ... COMMIT`, insert into `orders` **and** insert `{ event_id, type: 'OrderPlaced', payload }` into `outbox`. Either both commit or both roll back.
2. **Outbox Relay:** a background worker polls `outbox WHERE published_at IS NULL` (or tails Postgres WAL via Debezium CDC) and pushes messages to the broker.
3. **Idempotent Consumers:** because the relay provides **at-least-once** delivery, consumers record `processed_event_id` so duplicate deliveries are harmless no-ops.

## Real-world analogy
<Analogy>
Think of a **hotel front desk logbook**. When a guest checks in, the clerk writes the room assignment and drops a notification slip into the **physical outbox tray** in one motion. A bellhop (the relay) periodically empties the tray and delivers slips to housekeeping—even if the bellhop takes a break, no slip is lost.
</Analogy>

## Code
Writing business state and the outbox event in one SQL transaction:

```ts
// TypeScript 7.0.2 (illustrative SQL transaction)
export interface DbTx {
  exec(sql: string, params: unknown[]): Promise<void>;
}

export async function placeOrderWithOutbox(
  tx: DbTx,
  order: { id: string; customerId: string; totalCents: number },
) {
  await tx.exec(
    'INSERT INTO orders (id, customer_id, total_cents) VALUES ($1, $2, $3)',
    [order.id, order.customerId, order.totalCents],
  );

  const eventId = crypto.randomUUID();
  await tx.exec(
    'INSERT INTO outbox (id, event_type, payload) VALUES ($1, $2, $3)',
    [eventId, 'OrderPlaced', JSON.stringify(order)],
  );
}
```

## How to implement
<Steps>
  <Step>
    ### Create an `outbox` table
    Include `id` (UUID), `event_type`, `payload` (JSONB), `created_at`, and `published_at`.
  </Step>
  <Step>
    ### Write in the same transaction
    Insert into `outbox` inside the same DB transaction as your domain table.
  </Step>
  <Step>
    ### Relay and deduplicate
    Publish via polling (`FOR UPDATE SKIP LOCKED`) or Debezium CDC, and deduplicate by `event_id` on every consumer.
  </Step>
</Steps>

## Pros / Cons
