## TL;DR
Every remote call will eventually hang, fail, or arrive twice. Protect your service by combining **bounded timeouts** (shorter than your caller's), **bulkhead pool limits**, **jittered retries** (only on idempotent calls), a **circuit breaker**, and **explicit fallback behavior**.

## 1. Intent

<Intent>
Design outbound dependencies so a slow or broken downstream service degrades one feature cleanly instead of cascading into a full system outage.
</Intent>

## 2. Problem

Suppose your checkout API calls a third-party shipping-rate estimator. One afternoon the estimator accepts TCP connections but stops sending responses.

Without a timeout, every incoming request holds a worker thread or connection open indefinitely. Within 90 seconds the shared pool is full—now `/healthz`, `/orders`, and `/login` all fail too. Worse, a naive retry loop immediately hammers the struggling provider with 10× traffic, extending its outage.

## 3. Solution

Layer five complementary controls around every remote call:

| Failure mode | Control | Rule of thumb |
|---|---|---|
| **Slow** | **Timeout** | Always set connect + read timeouts shorter than your caller's deadline |
| **Transient error (503 / reset)** | **Retry + Jitter** | Exponential backoff + random jitter, max 2–3 attempts, never on `4xx` |
| **Persistent outage** | **Circuit Breaker** | Trip `OPEN` when failure rate spikes; fail fast in microseconds |
| **Duplicate delivery** | **Idempotency Key** | Store `Idempotency-Key` with a unique constraint before mutating |
| **Partial failure** | **Bulkhead + Degrade** | Cap concurrent calls per dependency; return cached/stale or queue async |

## 4. Real-world analogy

<Analogy>
Think of **watertight bulkheads and circuit breakers on a ship**. A circuit breaker trips immediately when a shorted wire draws too much current—preventing a fire—while watertight bulkheads ensure a leak in one compartment cannot flood the engine room and sink the whole vessel.
</Analogy>

## 7. Code

```ts
export async function fetchWithResilience<T>(
  url: string,
  options: { timeoutMs: number; maxAttempts: number; fallback: () => T },
): Promise<{ data: T; stale: boolean }> {
  for (let attempt = 0; attempt < options.maxAttempts; attempt++) {
    try {
      const res = await fetch(url, {
        signal: AbortSignal.timeout(options.timeoutMs),
      });

      if (res.status >= 400 && res.status < 500 && res.status !== 429) {
        // Never retry permanent 4xx client errors
        throw new Error(`Non-retryable client error: ${res.status}`);
      }
      if (!res.ok) {
        throw new Error(`Transient upstream error: ${res.status}`);
      }

      return { data: (await res.json()) as T, stale: false };
    } catch (err) {
      const isLast = attempt === options.maxAttempts - 1;
      if (isLast || (err instanceof Error && err.message.startsWith('Non-retryable'))) {
        return { data: options.fallback(), stale: true };
      }

      // Exponential backoff + full jitter prevents thundering herd
      const baseMs = 100 * 2 ** attempt;
      const jitterMs = Math.random() * baseMs;
      await new Promise((r) => setTimeout(r, jitterMs));
    }
  }

  return { data: options.fallback(), stale: true };
}
```

## 9. How to implement

<Steps>
  <Step>
    ### Set per-hop timeouts
    Ensure downstream timeouts are strictly smaller than your API's overall SLA budget.
  </Step>
  <Step>
    ### Isolate pools with bulkheads
    Limit concurrent in-flight requests per dependency so one slow provider cannot starve others.
  </Step>
  <Step>
    ### Add jittered retries for safe calls
    Retry only idempotent reads or `Idempotency-Key` writes on `5xx`/network errors, never `4xx`.
  </Step>
  <Step>
    ### Wrap with a circuit breaker and fallback
    Trip open on sustained errors and return an explicit degraded response or fail cleanly.
  </Step>
</Steps>
