## TL;DR
ORMs speed up everyday CRUD, but hide expensive **N+1 loops**, bloated `SELECT *` payloads, and awkward abstractions over joins or window functions. Use **eager batching (`include` / `with` / `IN (...)`)**, restrict raw-SQL escape hatches to **parameterized tagged templates** (never string interpolation), and **drop to SQL** for reporting, bulk writes, and tuned queries.

## Why it exists
Object-Relational Mappers bridge TypeScript objects and relational tables, generating typed queries and schema migrations. The abstraction leaks when developers treat database relations like in-memory arrays—triggering hundreds of network round trips per HTTP request or fighting the query builder to express a five-line SQL CTE.

## Mental model
Every ORM call still compiles to SQL and pays network round-trip latency plus database planning time. Think in **round trips and bytes transferred**, not object graphs.

## Do it

### 1. Fix the N+1 query with eager loading
Avoid `await` inside `for` loops or `Promise.all(rows.map(...))` that fires one query per row. Fetch relations in a single batched query instead:

```typescript
// Prisma / Drizzle-style TypeScript examples (not run)

// BAD (N+1): 1 query for orders + N queries for customer rows
const orders = await db.order.findMany({ take: 50 });
for (const order of orders) {
  order.customer = await db.customer.findUnique({ where: { id: order.customerId } });
}

// GOOD (Prisma-style): batched eager load + explicit field selection
const ordersWithCustomer = await db.order.findMany({
  take: 50,
  select: {
    id: true,
    totalCents: true,
    customer: { select: { id: true, name: true } },
  },
});

// GOOD (Drizzle-style): explicit SQL JOIN selecting only needed columns
const rows = await drizzleDb
  .select({
    orderId: ordersTable.id,
    totalCents: ordersTable.totalCents,
    customerName: customersTable.name,
  })
  .from(ordersTable)
  .innerJoin(customersTable, eq(ordersTable.customerId, customersTable.id))
  .limit(50);
```

### 2. Eager vs lazy loading
- **Eager loading** (`include`, `with`, or explicit `JOIN`): fetches related rows up front in 1–2 queries. Predictable latency, works cleanly with serverless/async handlers.
- **Lazy loading** (loading relations on property access): common in older active-record ORMs; almost always causes accidental N+1s in templates and JSON serializers. Disable implicit lazy loading if your ORM has it.

### 3. Raw-query escape hatches (safely)
When you need raw SQL, **never** use string interpolation inside `$queryRawUnsafe` or `sql.raw` with user input. Use tagged template literals so the ORM binds values as parameters (`$1`, `$2`)—see [SQL Injection & Parameterized Queries](/docs/security/sql-injection) for the full rules:

```typescript
// SAFE: tagged template binds `orgId` as $1 (not run)
const summary = await db.$queryRaw<Array<{ status: string; total: number }>>`
  SELECT status, COUNT(*)::int AS total
  FROM orders
  WHERE org_id = ${orgId}
  GROUP BY status
`;
```

### 4. When to drop to SQL
Drop down to raw SQL (or a typed query runner) when:
- You need **window functions** (`ROW_NUMBER()`, `SUM() OVER (...)`), **CTEs (`WITH`)**, or `LATERAL` joins.
- You are doing **bulk upserts** or batch updates across thousands of rows.
- You are tuning a hot query with `EXPLAIN (ANALYZE, BUFFERS)` and need exact control over join order or `SELECT ... FOR UPDATE SKIP LOCKED`.

## When you DON'T need an ORM
- **Analytics, reporting, or SQL-first teams:** If most of your endpoints are custom aggregations or your team is already fluent in SQL, a thin typed driver (`postgres` / `pg`) or query builder (Kysely) avoids fighting ORM abstractions.
- **Simple scripts or static builds:** A 50-line migration or CLI script does not need a code-generated ORM client.
- **Cost / complexity trade-off:** ORMs eliminate repetitive CRUD boilerplate and keep TypeScript types in sync with your schema, at the cost of a learning curve around generated SQL, migration tooling, and occasional escape hatches.

## Gotchas
- **Over-fetching with `SELECT *`:** Loading entire user or JSONB columns when you only need `id` and `email` wastes DB I/O and prevents PostgreSQL Index-Only Scans.
- **Silent in-memory filtering:** Writing `.findMany()` and then `.filter(...)` in JavaScript instead of `WHERE` in SQL pulls the whole table over the network.
- **Unbounded `include`:** Eager-loading 4 levels of nested one-to-many relations can blow up memory and response times.

## Production checklist
- [ ] Query logging or OpenTelemetry tracing is enabled in dev/staging to catch N+1 query spikes per request.
- [ ] List queries select only the columns needed (`select` / projection) and always enforce a `LIMIT`.
- [ ] Lint/review rules ban `$queryRawUnsafe` and `sql.raw` with template interpolation.
- [ ] Heavy reporting and queue-worker queries (`SKIP LOCKED`) use parameterized SQL directly.
