## TL;DR
There is no universally "best" architecture—only a match between **what property you are buying** (latency, independent deploys, domain isolation, or speed) and **what operational cost you can afford**. Prefer **reversible choices** inside one deployable, decide **multi-tenancy** upfront, and record every trade-off in an **ADR**.

## Why it exists
Applying one "gold-standard" template (such as event-sourced microservices with CQRS) to every project wastes months on simple CRUD apps and adds latency to low-latency paths. Architecture should answer a forced question: *which specific constraint are we solving right now?*

## Comparison table: what property are you buying?

| Property you need | Structure that buys it | Main cost |
|---|---|---|
| **Fastest time to first release** | Layered monolith | Domain rules can couple to DB/ORM over time |
| **Testable business logic independent of frameworks** | Hexagonal / Clean (per module) | Extra ports, adapters, and mapping code |
| **Independent deployment & team scaling** | Modular monolith → separate services | Network latency, distributed tracing, 3–5× ops overhead |
| **Lowest possible request latency** | Single process, fewest network hops | Shares failure domain and deploy cadence |
| **Temporal decoupling & replay** | Event-driven / Outbox | Eventual consistency, schema evolution, dead-letter handling |
| **Full audit history of every state change** | Event sourcing | Projection rebuilds, steep learning curve, hard to reverse |

## Reversibility matrix

| Decision | Reversibility | Practical rule |
|---|---|---|
| **Folder & module boundaries** | Hours to days | Decide quickly; refactor as you learn |
| **Layered → Hexagonal inside one app** | Days to weeks | Adopt incrementally on complex modules only |
| **Monolith → extract one service** | Weeks | Easy later if module boundaries were kept clean |
| **Microservices → merge back to monolith** | Quarters | Expensive; don't split before team or scale forces you |
| **CRUD state → Event Sourcing** | Quarters | Very hard to undo; require a genuine audit/replay driver |
| **Primary database & multi-tenancy model** | Years | Effectively permanent; decide deliberately upfront |

## Gotchas
- **Standardizing on one template estate-wide:** A 6-table internal admin tool does not need CQRS and Kafka just because the core billing engine uses them.
- **Deferring multi-tenancy:** Adding `tenant_id` and row-level isolation after launch means rewriting almost every query and index.
- **Unrecorded decisions:** Without an ADR listing rejected options and revisit triggers, future teams either blindly copy the old pattern or rewrite it without knowing why it existed.

## Production checklist
- [ ] Name the specific property you are buying (latency, testability, independent deploy) before picking an architecture.
- [ ] Mix styles per module inside one deployable (e.g., Hexagonal for pricing/billing, simple CRUD for reference tables).
- [ ] Decide multi-tenancy and data-residency boundaries before writing schema migrations.
- [ ] Write a short ADR with context, consequences, rejected options, and a concrete revisit trigger.
