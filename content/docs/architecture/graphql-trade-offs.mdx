## TL;DR
Adopt **GraphQL** when a client screen must stitch multiple backends in one round trip with flexible field selection. Never ship a production graph without **per-request DataLoader batching**, **depth/complexity limits** (or **persisted queries**), **nullable remote fields**, and **operation-level logging**.

## Why it exists
Complex dashboards often suffer from multi-hop REST waterfalls (fetch user → fetch accounts → fetch recent orders) or over-fetching huge payloads over slow connections. A GraphQL BFF/gateway collapses those into one typed request.

## Mental model
GraphQL replaces multiple URLs with one typed graph—meaning **caching, rate limiting, and audit logging** move from HTTP routes into your validation and resolver layers.

## Do it

### 1. Design nullability for partial failure
Make structural invariants (`id`, `createdAt`) non-null (`!`), and keep fields backed by separate microservices **nullable** so a single service outage degrades one panel rather than blanking the entire `data` payload:

```graphql
type AccountOverview {
  id: ID!
  displayName: String!
  recentOrders: OrderConnection   # Nullable: orders-api outage won't wipe the whole screen
  creditScore: Int                # Nullable: risk-api timeout degrades cleanly
}
```

### 2. Per-request DataLoader (never shared across requests)
Always construct DataLoaders inside the per-request `context` factory so cached entities never leak between users, and ensure your batch function aligns results with the exact order of `keys`:

```ts
// Per-request context: safe isolation + N+1 batching
export function createLoaders(ordersApi: OrdersClient) {
  return {
    ordersByAccount: new DataLoader<string, Order[]>(async (accountIds) => {
      const rows = await ordersApi.batchByAccountIds([...accountIds]);
      const grouped = new Map<string, Order[]>();
      for (const row of rows) {
        const list = grouped.get(row.accountId) ?? [];
        list.push(row);
        grouped.set(row.accountId, list);
      }
      // Must return one entry per key in the exact input order
      return accountIds.map((id) => grouped.get(id) ?? []);
    }),
  };
}
```

## Gotchas
- **POST-only breaks CDN/HTTP caching:** Standard `POST /graphql` bypasses `GET` HTTP caches; use persisted queries over `GET` if you need edge caching.
- **Unbounded nested cycles:** Without depth/complexity limits, a cyclic query (`user -> orders -> user -> orders`) can trigger exponential backend fan-out.
- **Opaque `POST /graphql 200` access logs:** Log the GraphQL operation name, trace ID, and sensitive field access explicitly in resolvers for auditability.

## Production checklist
- [ ] Instantiate DataLoaders per request (never at module scope) and test key-order alignment with missing keys.
- [ ] Enforce maximum query depth, query complexity, or strict persisted-query allow-lists.
- [ ] Disable GraphQL introspection in production for external-facing endpoints.
- [ ] Keep remote-service fields nullable so partial failures do not cascade to `data: null`.
