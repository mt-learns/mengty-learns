## TL;DR
Tactical DDD puts business invariants inside the domain model instead of anemic service scripts: **Value Objects** (`Money`) are immutable, **Entities** (`Order`) have identity, **Aggregates** guard consistency boundaries, **Repositories** persist whole aggregates, and **Domain Events** (`OrderPlaced`) announce state changes.

## Intent
<Intent>
Enforce business invariants in one place inside an **Aggregate Root** (like `Order`) so invalid state—such as an empty order or a negative total—cannot be constructed anywhere in the codebase.
</Intent>

## Problem
In an "anemic domain model", `Order` is just a plain data bag (`interface Order { status: string; items: any[] }`) and validation rules scatter across controllers, cron jobs, and services. One endpoint forgets to check `items.length > 0` or recalculates `totalCents` differently, corrupting data in production.

## Solution
Tactical DDD gives you five building blocks that fit naturally inside Hexagonal or Clean Architecture:

1. **Value Object (`Money`):** immutable, validated on creation (`amountCents >= 0`), compared by value.
2. **Entity (`Order`, `OrderLine`):** has a unique `id` and mutable lifecycle (`draft` → `placed` → `cancelled`).
3. **Aggregate Root (`Order`):** owns `OrderLine[]` and exposes intent-revealing methods (`order.place()`). No outside code mutates `order.lines` directly.
4. **Repository (`OrderRepository`):** saves and loads the entire `Order` aggregate as one atomic unit.
5. **Domain Event (`OrderPlaced`):** immutable record emitted by the aggregate when a meaningful business fact occurs.

## Real-world analogy
<Analogy>
Think of a **locked shipping container** (Aggregate) with a **manifest clerk** (Aggregate Root). You cannot reach through the wall to swap one box (`OrderLine`); you hand a request to the clerk, who checks weight limits (invariants), updates the manifest, seals the container, and stamps a dispatch slip (Domain Event).
</Analogy>

## Code
The shared `Order` example modeled as a Value Object (`Money`), Aggregate Root (`Order`), and Domain Event (`OrderPlaced`):

```ts
// TypeScript 7.0.2
export class Money {
  private constructor(
    public readonly cents: number,
    public readonly currency: 'USD' | 'EUR',
  ) {}

  static of(cents: number, currency: 'USD' | 'EUR' = 'USD'): Money {
    if (!Number.isInteger(cents) || cents < 0) throw new Error('Invalid Money');
    return new Money(cents, currency);
  }

  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error('Currency mismatch');
    return Money.of(this.cents + other.cents, this.currency);
  }
}

export interface OrderPlaced {
  readonly type: 'OrderPlaced';
  readonly orderId: string;
  readonly totalCents: number;
}

export class Order {
  private events: OrderPlaced[] = [];

  private constructor(
    public readonly id: string,
    private readonly items: ReadonlyArray<{ sku: string; price: Money; qty: number }>,
    private status: 'draft' | 'placed',
  ) {}

  static create(id: string, items: Array<{ sku: string; price: Money; qty: number }>): Order {
    if (items.length === 0) throw new Error('Order must have at least one item');
    return new Order(id, items, 'draft');
  }

  place(): OrderPlaced[] {
    if (this.status !== 'draft') throw new Error('Order already placed');
    this.status = 'placed';
    const total = this.items.reduce(
      (sum, item) => sum.add(Money.of(item.price.cents * item.qty, item.price.currency)),
      Money.of(0),
    );
    this.events.push({ type: 'OrderPlaced', orderId: this.id, totalCents: total.cents });
    return [...this.events];
  }
}
```

## When to use / when to avoid
<Checklist
  use={[
    'Your domain has real state-transition rules and invariants (orders, payments, inventory reservations, bookings).',
    'You already use Hexagonal or Clean Architecture and want a rich domain core instead of anemic DTOs.',
  ]}
  avoid={[
    'Simple CRUD forms or admin tables with no invariants—tactical DDD adds ceremony for zero payoff.',
    'Reporting/analytics queries—bypass Aggregates and read directly with SQL.',
  ]}
/>

## How to implement
<Steps>
  <Step>
    ### Extract Value Objects first
    Replace raw `number` or `string` primitives (`cents`, `email`, `currency`) with self-validating Value Objects.
  </Step>
  <Step>
    ### Keep Aggregates small
    Include only the child entities needed to enforce an immediate invariant; reference other Aggregates by ID only.
  </Step>
  <Step>
    ### Emit Domain Events on state transitions
    Record events inside the Aggregate Root and publish them after the repository commits.
  </Step>
</Steps>
