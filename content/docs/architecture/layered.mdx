## 1. Intent

<Intent>
Separate an application into horizontal technical layers—**Presentation**, **Business**, and **Data**—so UI handling, business rules, and database queries do not live in the same file, with dependencies flowing strictly downward.
</Intent>

## 2. Problem

When a small Order API grows inside route handlers, HTTP parsing, discount rules, tax math, and SQL queries end up tangled together. Changing a table column breaks validation; testing a discount calculation requires a running Postgres instance.

Over time, two classic layered pitfalls appear even after splitting files:

1. **Leaky layers:** A controller bypasses the business layer and queries the database directly, or the business layer accepts raw HTTP `Request` objects.
2. **Database-centric design:** Because Business depends on Data, and Data mirrors SQL tables, domain models turn into thin wrappers around database rows instead of expressing business rules.

## 3. Solution

Group code by **technical responsibility** into stacked horizontal layers:

- **Presentation:** Parses HTTP requests, validates input shapes, and formats JSON responses.
- **Business (Domain / Service):** Enforces Order rules—stock checks, totals, and discounts—without knowing about HTTP status codes or SQL syntax.
- **Data (Persistence):** Reads and writes `orders` rows in Postgres.

Each layer only talks to the layer immediately below it. Presentation calls Business; Business calls Data; Data talks to Postgres.

## 4. Real-world analogy

<Analogy>
Think of a restaurant with a **waiter** (Presentation), a **chef** (Business), and a **pantry clerk** (Data). The customer never walks into the pantry to grab ingredients, and the chef does not take payments at the table. Each station hands work to the next station down the line.
</Analogy>

## 6. Structure: Dependency Rule

In classic Layered architecture, **dependencies point top-down**. Presentation depends on Business, and Business depends on Data.

```ts
// --- Data Layer (src/data/order-repo.ts) ---
export interface OrderRow {
  id: string;
  customerId: string;
  totalCents: number;
}

export class OrderRepo {
  async insert(customerId: string, totalCents: number): Promise<OrderRow> {
    // Simulated Postgres INSERT
    return { id: 'ord_101', customerId, totalCents };
  }
}

// --- Business Layer (src/business/order-service.ts) ---
export interface OrderItemInput {
  priceCents: number;
  qty: number;
}

export class OrderService {
  constructor(private readonly repo: OrderRepo) {}

  async placeOrder(customerId: string, items: OrderItemInput[]): Promise<OrderRow> {
    if (items.length === 0) {
      throw new Error('Order must contain at least one item');
    }
    const totalCents = items.reduce((sum, item) => sum + item.priceCents * item.qty, 0);
    return this.repo.insert(customerId, totalCents);
  }
}

// --- Presentation Layer (src/presentation/order-controller.ts) ---
export class OrderController {
  constructor(private readonly service: OrderService) {}

  async handlePost(body: { customerId: string; items: OrderItemInput[] }) {
    const order = await this.service.placeOrder(body.customerId, body.items);
    return { status: 201, data: order };
  }
}
```

## 8. When to use / when to avoid

<Checklist
  use={[
    'You are building a straightforward CRUD app or internal admin tool with simple domain rules.',
    'The team is small and wants a familiar folder layout (controllers, services, repositories) on day one.',
    'Database schema and business objects map closely without complex invariants.',
  ]}
  avoid={[
    'Business rules are rich and need fast unit tests with zero database or ORM setup.',
    'You need to swap databases, message brokers, or external APIs without touching business logic.',
    'The app is large enough that horizontal layers create a big ball of mud across features.',
  ]}
/>

## 9. How to implement

<Steps>
  <Step>
    ### Split folders by horizontal layer
    Create `presentation/`, `business/`, and `data/` directories so team members know where each responsibility belongs.
  </Step>
  <Step>
    ### Keep HTTP types out of Business
    Parse request bodies and set HTTP status codes in Presentation; pass plain TypeScript objects into `OrderService`.
  </Step>
  <Step>
    ### Enforce downward-only imports
    Add an ESLint import rule so `presentation/` never imports `data/` directly, preventing leaky shortcuts.
  </Step>
  <Step>
    ### Watch for DB-centric drift
    When `OrderService` starts returning raw ORM models with lazy-loaded relations, consider introducing [Dependency Inversion](/docs/architecture/dependency-inversion) or [Hexagonal Architecture](/docs/architecture/hexagonal).
  </Step>
</Steps>

## 10. Pros / Cons

<ProsCons
  pros={[
    'Minimal boilerplate and fast to scaffold for CRUD-heavy services.',
    'Every developer immediately recognizes the Controller → Service → Repository flow.',
    'Easy to enforce basic separation of concerns in small codebases.',
  ]}
  cons={[
    'Business logic depends directly on the Data layer, making pure domain unit tests harder.',
    'Layers often turn into pass-throughs ("sinkhole" anti-pattern) that add files without logic.',
    'Schema changes in the database ripple upward into business services.',
  ]}

<MyTake>
Layered architecture is my default starting point for small APIs and prototypes. It only starts hurting when `OrderService` becomes a maze of ORM queries and mocking the database takes more lines than the test itself—that is my signal to invert the repository dependency.
</MyTake>
