## TL;DR
*"We need to refactor"* loses every planning meeting. Measure debt's **interest**—extra lead time, incident share, and rework rate—put quantified debt tickets in the **same backlog** as features, and repay high-interest modules incrementally using **characterization tests + Strangler Fig** instead of big-bang rewrites.

## Why it exists
When engineering describes debt with adjectives ("messy", "ugly"), product managers hear "engineering taste" and prioritize revenue features instead—until a critical change takes 14 weeks instead of 2 and misses a hard deadline.

## Do it

### Measure the interest before asking for capacity
- **Delivery drag:** Median PR lead time in module X (e.g., 9 days) vs. rest of repo (2 days).
- **Incident share:** Percentage of production incidents traced to module X over the last 2 quarters.
- **Rework rate:** Percentage of tickets touching module X that needed a bugfix within 30 days.

### Repay safely: characterization tests + Strangler Fig
1. **Pin current behavior** with characterization tests around the legacy boundary.
2. **Route new cases** to the clean implementation behind a feature flag.
3. **Migrate one slice at a time** and delete the legacy path once traffic is 100% migrated.

## Gotchas
- **Tracking debt in a separate wiki page:** If it isn't in the same backlog as features, it doesn't exist during sprint planning.
- **`TODO` comments without ticket IDs:** Orphaned `TODO`s rot forever—require `TODO(ENG-123)` in code review.
- **Big-bang rewrites:** Rewriting a live system from scratch while features keep landing on the old one rarely catches up.

## Production checklist
- [ ] Attach measured lead-time, incident, or rework numbers to every structural debt ticket.
- [ ] Keep debt tickets in the main product backlog alongside features.
- [ ] Protect a standing capacity slice (e.g. 15–20%) or require opportunistic cleanup on every touch.
- [ ] Write characterization tests before refactoring untested legacy modules.
