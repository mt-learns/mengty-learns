## TL;DR
When two teams deploy on independent schedules, mocked integration tests only prove your code matches *your guess* about the other API. **Contract testing** (consumer-driven **Pact** for internal services, **OpenAPI diff / `buf breaking`** at partner/gRPC edges) catches breaking schema drift in CI *before* merge.

## Why it exists
A provider team renames or removes a nullable field and updates its own tests—all green. Meanwhile, the consumer team's MSW mocks still return the old field—all green. Both deploy, and production crashes with `undefined` until a customer calls.

## Do it

| Boundary | Recommended contract check |
|---|---|
| **Internal REST (known teams)** | Consumer-driven **Pact** + Pact Broker + `can-i-deploy` gate |
| **External / Partner REST** | `openapi-diff --fail-on-incompatible` + provider response schema validation |
| **Internal gRPC** | `buf breaking --against main` on `.proto` files |
| **GraphQL** | `graphql-inspector diff` checking live field usage before removing `@deprecated` fields |

## Gotchas
- **Over-specifying contracts:** Matching exact timestamps or array lengths in Pact turns harmless provider changes into false failures—use type/regex matchers (`like`, `eachLike`).
- **Running Pact without `can-i-deploy`:** Publishing contracts without blocking deploys turns failures into ignored notifications.
- **Expecting contract tests to catch business bugs:** Changing `price` from `100` (cents) to `1.00` (dollars) passes a `number` type check—keep semantic tests in unit/integration suites.

## Production checklist
- [ ] Gate partner OpenAPI specs with `openapi-diff` and `.proto` files with `buf breaking` in CI.
- [ ] Use Pact + `can-i-deploy` when independent internal teams ship frontend/BFF and backend APIs separately.
- [ ] Match shapes and types in contracts rather than brittle literal values.
