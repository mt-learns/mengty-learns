## TL;DR
A CI/CD pipeline is an event-driven DAG: a **trigger** (`push`, `pull_request`) spawns **jobs** on clean runners, **caches** restore unchanged dependencies, **artifacts** carry build outputs across stages, and a **deploy gate** promotes only verified builds.

## Intent
<Intent>
Understand the five building blocks of every modern CI/CD pipeline—triggers, parallel jobs, caching, artifacts, and deploy gates—using this repository's own `.github/workflows/ci.yml` as a concrete reference.
</Intent>

## Problem
Treating CI as one opaque bash script makes builds slow and brittle. Installing packages from scratch on every commit wastes minutes, running lint/test/build sequentially delays feedback, and deploying without a gate lets broken commits reach users.

## Solution
Every healthy pipeline separates five responsibilities:

1. **Trigger (`on:`):** Declarative rules (`push` to `main`, `pull_request`) decide when the workflow starts.
2. **Parallel Jobs (`jobs:`):** Independent checks (lint, typecheck, unit tests, build) run concurrently on separate runners unless linked by `needs:`.
3. **Cache Restore / Save:** Package stores (like `pnpm` store keyed by `pnpm-lock.yaml`) are restored before `pnpm install --frozen-lockfile` and saved afterward.
4. **Artifacts:** Build outputs (`out/`), Playwright traces, or coverage reports are uploaded so downstream jobs or reviewers can inspect or deploy them.
5. **Deploy Gate:** Branch protection and environment rules require all check jobs to succeed before the deploy step runs.

## Real-world analogy
<Analogy>
Think of an airport security and boarding line: your ticket scan (**trigger**) starts the process; baggage screening and passport check (**parallel jobs**) happen at separate lanes; TSA PreCheck (**cache**) lets frequent flyers skip unpacking; your boarding pass (**artifact**) is handed to the **deploy gate** agent before you step onto the plane.
</Analogy>

## Code
Here is the real `.github/workflows/ci.yml` from this repository:

```yaml
name: CI

on:
  push:
    branches: [main, mengtylearns-mvp]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 11.6.0
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm typecheck
      - run: pnpm build
```

## When to use / when to avoid
<Checklist
  use={[
    'You want fast feedback by running independent checks (lint, unit tests, build) in parallel.',
    'You need reproducible builds using --frozen-lockfile and cached dependency stores.',
  ]}
  avoid={[
    'Splitting a 20-second workflow into 6 tiny jobs where runner boot + checkout overhead exceeds the work saved.',
    'Storing secrets inside caches or artifacts—both are accessible to workflow runs and should never hold credentials.',
  ]}
/>

## How to implement
<Steps>
  <Step>
    ### Define narrow triggers
    Trigger on `pull_request` and pushes to `main` so every merge candidate is checked.
  </Step>
  <Step>
    ### Cache dependencies by lockfile hash
    Use `actions/setup-node` with `cache: pnpm` and `pnpm install --frozen-lockfile`.
  </Step>
  <Step>
    ### Gate deployment on check jobs
    Require `lint`, `typecheck`, `test`, and `build` to pass before deploying artifacts.
  </Step>
</Steps>

## Pros / Cons
<ProsCons
