## 1. Intent

<Intent>
Attach additional responsibilities to an object dynamically by wrapping it inside one or more **Decorator** objects that implement the exact same interface as the core component.
</Intent>

## 2. Problem

Suppose you have an `HttpClient` interface with a single `request(url)` method. Over time, different services need combinations of retries on 503s, in-memory response caching, and structured request logging.

If you add those combinations via inheritance (`RetryingHttpClient`, `CachedHttpClient`, `LoggedCachedRetryingHttpClient`), every new feature doubles the number of subclasses. Even worse, you cannot toggle caching or retries per environment at runtime without building yet another subclass.

## 3. Solution

Create wrapper classes (`LoggingDecorator`, `CacheDecorator`, `RetryDecorator`) that all implement the same `HttpClient` interface and take another `HttpClient` in their constructor.

Each decorator runs its own pre- and post-processing around `this.inner.request(req)`. Because every wrapper looks like an `HttpClient` from the outside, you can stack them in any order at startup without changing caller code.

## 4. Real-world analogy

<Analogy>
Think of HTTP reverse-proxy middleware (or Russian nesting dolls). A request enters the outer logging layer, passes through the rate-limiter and cache layers, hits the upstream server, and then the response travels back out through the same layers in reverse order.
</Analogy>

## 7. Code

<Tabs items={['TypeScript']}>
  <Tab value="TypeScript">
```ts
interface HttpRequest {
  method: 'GET' | 'POST';
  url: string;
}

interface HttpResponse {
  status: number;
  body: string;
}

// Component interface
interface HttpClient {
  request(req: HttpRequest): Promise<HttpResponse>;
}

// Concrete Component
class FetchHttpClient implements HttpClient {
  async request(req: HttpRequest): Promise<HttpResponse> {
    return { status: 200, body: `ok:${req.method}:${req.url}` };
  }
}

// Decorator 1: Retry transient failures
class RetryHttpClient implements HttpClient {
  constructor(
    private readonly inner: HttpClient,
    private readonly maxAttempts = 3,
  ) {}

  async request(req: HttpRequest): Promise<HttpResponse> {
    let lastError: unknown;
    for (let attempt = 1; attempt <= this.maxAttempts; attempt++) {
      try {
        const res = await this.inner.request(req);
        if (res.status < 500 || attempt === this.maxAttempts) return res;
      } catch (err) {
        lastError = err;
        if (attempt === this.maxAttempts) throw lastError;
      }
    }
    throw lastError;
  }
}

// Decorator 2: In-memory GET cache
class CachedHttpClient implements HttpClient {
  private readonly cache = new Map<string, HttpResponse>();

  constructor(private readonly inner: HttpClient) {}

  async request(req: HttpRequest): Promise<HttpResponse> {
    if (req.method === 'GET') {
      const hit = this.cache.get(req.url);
      if (hit) return hit;
    }
    const res = await this.inner.request(req);
    if (req.method === 'GET' && res.status === 200) {
      this.cache.set(req.url, res);
    }
    return res;
  }
}

// Decorator 3: Structured logging
class LoggingHttpClient implements HttpClient {
  constructor(private readonly inner: HttpClient) {}

  async request(req: HttpRequest): Promise<HttpResponse> {
    const start = Date.now();
    const res = await this.inner.request(req);
    console.log(`[http] ${req.method} ${req.url} -> ${res.status} (${Date.now() - start}ms)`);
    return res;
  }
}

// Compose stack: Logging -> Cache -> Retry -> FetchHttpClient
const client: HttpClient = new LoggingHttpClient(
  new CachedHttpClient(
    new RetryHttpClient(new FetchHttpClient(), 3),
  ),
);

await client.request({ method: 'GET', url: 'https://api.example.com/health' });
```

## 8. When to use / when to avoid

<Checklist
  use={[
    'You need to compose optional, orthogonal behaviors (logging, caching, retries, auth headers) in different combinations at runtime.',
    'You cannot or should not subclass the core component (e.g. third-party classes or final-like modules).',
    'Each cross-cutting concern should stay small and testable in isolation.',
  ]}
  avoid={[
    'Wrapper order is implicit and error-prone without clear documentation (e.g. caching *outside* auth leaks tenant responses).',
    'You need to inspect or remove a specific middle layer dynamically after construction.',
    'A simple middleware array or pipeline function (`middlewares.reduceRight(...)`) is cleaner than nested `new A(new B(new C()))`.',
  ]}
/>

### When NOT to use it

Overengineering occurs when you wrap a single concrete class in three decorators that are *always* used together in the exact same order. If nobody ever composes them differently, a single well-factored class (or a small helper function) is far easier to read than four constructor-chained wrappers.

### Real-world example in this stack

In Next.js (`next.config.mjs`) and Fumadocs (`lib/source.ts`), configuration and loader plugins wrap base config objects with additional capabilities (MDX compilation, search indexing) while preserving the underlying config contract.

## 9. How to implement

<Steps>
  <Step>
    ### Define the Component interface
    Keep the contract (`HttpClient.request`) narrow so every wrapper is easy to implement.
  </Step>
  <Step>
    ### Implement the Concrete Component
    Write the core `FetchHttpClient` with zero logging, caching, or retry logic.
  </Step>
  <Step>
    ### Create Decorators wrapping `HttpClient`
    Each decorator implements `HttpClient`, accepts `inner: HttpClient`, and delegates to `this.inner.request(req)`.
  </Step>
  <Step>
    ### Document and wire the stack order
    Assemble the chain at your composition root (`Logging -> Cache -> Retry -> Fetch`) and verify order-dependent interactions.
  </Step>
</Steps>

## 10. Pros / Cons

<ProsCons
  pros={[
    'Compose behaviors dynamically without combinatorial subclassing.',
    'Single Responsibility Principle: each wrapper handles one cross-cutting concern.',
    'Open/Closed Principle: add a new wrapper (e.g. circuit breaker) without touching existing wrappers.',
  ]}
  cons={[
    'Deeply nested `new A(new B(new C()))` construction is noisy to read.',
    'Order-dependent bugs (e.g. Retry outside Cache vs Cache outside Retry) can be subtle.',
    'Hard to remove a specific inner decorator once the stack is built.',
  ]}
/>

## 12. Check yourself

<MyTake>
Pay close attention to wrapper order. Putting `Cache` *outside* `Retry` means cache hits skip retries entirely (good), whereas putting `Logging` *inside* `Cache` hides cache hits from your logs (usually surprising).
</MyTake>
