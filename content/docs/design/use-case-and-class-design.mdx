## TL;DR
Before writing code for a non-trivial workflow, capture a **use case** (actor, preconditions, main flow, exception flows, postconditions), then extract **nouns** into cohesive domain classes that own their own invariants rather than anemic data bags.

## Why it exists
Jumping straight from a one-line ticket ("Cancel an invoice") to database tables leaves authorization, concurrency, and rollback behavior undefined. Each developer guesses differently, and QA discovers missing rules after implementation.

## Do it

### Step 1: Write a lightweight use case
Example: **Cancel Paid Invoice**
- **Primary actor:** Operations Manager
- **Preconditions:** User is authenticated and holds `invoice.cancel` permission; invoice exists.
- **Main flow:**
  1. Manager submits invoice ID and cancellation reason.
  2. System checks permission and verifies invoice status is `PAID`.
  3. System transitions invoice to `CANCELLED`, records reason + timestamp, and emits an audit event.
- **Exception flows:**
  - *E1 (Unauthorized):* Return `403 Forbidden`; no state change.
  - *E2 (Already cancelled or refunded):* Reject with `409 Conflict`.
- **Postconditions:** Invoice status is `CANCELLED`; audit log entry persisted.

### Step 2: Assign behavior to the object that owns the data
Avoid putting every rule in a giant `InvoiceManager` while `Invoice` is just `{ id, status }`:

```ts
export class Invoice {
  private constructor(
    public readonly id: string,
    private _status: 'DRAFT' | 'PAID' | 'CANCELLED',
    private _cancelReason?: string,
  ) {}

  static paid(id: string): Invoice {
    return new Invoice(id, 'PAID');
  }

  get status() {
    return this._status;
  }

  cancel(reason: string): void {
    if (this._status !== 'PAID') {
      throw new Error(`Cannot cancel invoice in status ${this._status}`);
    }
    if (reason.trim().length < 5) {
      throw new Error('Cancellation reason must be at least 5 characters');
    }
    this._status = 'CANCELLED';
    this._cancelReason = reason.trim();
  }
}
```

## Gotchas
- **Skipping exception flows:** If you only specify the happy path, error codes, idempotency, and partial-failure rollbacks get invented inconsistently at 2 a.m.
- **Anemic entities:** Putting `invoice.status = 'CANCELLED'` directly in a controller lets another endpoint mutate status without checking invariants.
- **Over-modeling trivial CRUD:** A simple tag or lookup table does not need a formal use-case document—save this for workflows with permissions, state transitions, or money/inventory invariants.

## Production checklist
- [ ] Every non-trivial workflow lists preconditions, main flow, exception flows, and postconditions.
- [ ] Domain invariants (like `cancel()` preconditions) live inside the entity, not scattered across controllers.
- [ ] QA test cases trace directly to both the main flow and every exception flow.
