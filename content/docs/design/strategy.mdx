## 1. Intent

<Intent>
Extract a family of interchangeable algorithms into separate units behind one interface, so a **Context** can swap how it performs a task at runtime without conditional branching.
</Intent>

## 2. Problem

Suppose you are building a deployment runner for a platform team. At first it only performs rolling updates. Later, product teams ask for blue-green cutovers for zero-downtime databases, and canary rollouts that shift 10% of traffic before full promotion.

If all three rollout algorithms live inside `DeployRunner` behind an `if/else` or `switch` statement, every new rollout mode forces you to edit and retest the core runner. The class grows hard to read, and unrelated deployment logic becomes tightly coupled.

## 3. Solution

Define a common `DeployStrategy` interface with a single `execute(release)` method. Move each rollout algorithm into its own class (`RollingStrategy`, `BlueGreenStrategy`, `CanaryStrategy`) implementing that interface.

`DeployRunner` (the **Context**) holds a reference to a `DeployStrategy` and delegates the rollout step to it. The caller decides which strategy to inject or swap at runtime, so `DeployRunner` never needs to know which rollout algorithm is active.

## 4. Real-world analogy

<Analogy>
Think of a CI/CD pipeline artifact uploader. The pipeline orchestrator knows *when* to publish build artifacts, but *how* they are uploaded depends on the target: S3 multipart upload, container registry push, or local filesystem copy. Swapping the upload driver does not change how the pipeline builds or tests the code.
</Analogy>

## 7. Code

<Tabs items={['TypeScript (Classes)', 'TypeScript (Functions)']}>
  <Tab value="TypeScript (Classes)">
```ts
interface Release {
  service: string;
  version: string;
}

interface DeployResult {
  mode: string;
  summary: string;
}

// Strategy interface
interface DeployStrategy {
  execute(release: Release): Promise<DeployResult>;
}

// Concrete strategies
class RollingStrategy implements DeployStrategy {
  constructor(private readonly maxUnavailable = 1) {}

  async execute(release: Release): Promise<DeployResult> {
    return {
      mode: 'rolling',
      summary: `Rolled out ${release.service}@${release.version} (maxUnavailable=${this.maxUnavailable})`,
    };
  }
}

class BlueGreenStrategy implements DeployStrategy {
  async execute(release: Release): Promise<DeployResult> {
    return {
      mode: 'blue-green',
      summary: `Booted green environment for ${release.service}@${release.version} and switched router`,
    };
  }
}

class CanaryStrategy implements DeployStrategy {
  constructor(private readonly trafficPercent: number) {}

  async execute(release: Release): Promise<DeployResult> {
    return {
      mode: 'canary',
      summary: `Shifted ${this.trafficPercent}% traffic to ${release.service}@${release.version}`,
    };
  }
}

// Context
class DeployRunner {
  constructor(private strategy: DeployStrategy) {}

  setStrategy(strategy: DeployStrategy): void {
    this.strategy = strategy;
  }

  async deploy(release: Release): Promise<DeployResult> {
    return this.strategy.execute(release);
  }
}

// Usage: swap strategies at runtime
const runner = new DeployRunner(new RollingStrategy(2));
await runner.deploy({ service: 'api', version: '1.4.0' });

runner.setStrategy(new CanaryStrategy(10));
await runner.deploy({ service: 'api', version: '1.5.0-rc1' });
```
  </Tab>
  <Tab value="TypeScript (Functions)">
```ts
interface Release {
  service: string;
  version: string;
}

// When strategies are stateless, a function type avoids class boilerplate
type DeployFn = (release: Release) => Promise<string>;

const rollingDeploy: DeployFn = async (r) => `rolling:${r.service}@${r.version}`;
const blueGreenDeploy: DeployFn = async (r) => `blue-green:${r.service}@${r.version}`;

async function runDeploy(release: Release, deployFn: DeployFn): Promise<string> {
  return deployFn(release);
}

await runDeploy({ service: 'web', version: '2.0.0' }, blueGreenDeploy);
```

## 8. When to use / when to avoid

<Checklist
  use={[
    'You need to swap how an object performs a task at runtime (e.g. rolling vs canary deploy, compression codec, or retry backoff).',
    'A class has a growing switch/if-else block selecting between variants of the same operation.',
    'You want to isolate complex algorithm state (like canary traffic percentages) from the caller.',
  ]}
  avoid={[
    'You only have two simple variants that rarely change—a plain conditional is easier to read.',
    'Strategies are stateless one-liners; pass a plain callback function instead of creating classes.',
    'Callers have no reason to know the difference between strategies—hide the choice inside a factory.',
  ]}
/>

### When NOT to use it

Overengineering shows up when every single `if` statement gets turned into a `Strategy` interface plus three single-method classes. If you have two branches that are three lines each and have not changed in a year, keep the `if/else`. In TypeScript, if a strategy has no configuration or internal state, a function parameter (`(input) => output`) gives you the exact same decoupling with zero class ceremony.

In this site's diagram renderer (`components/diagram/layout.ts`), the layout engine switches between `'flow'` (dagre left-to-right or top-to-bottom) and `'tree'` (hierarchical bus layout) via `FlowLayoutMode` without duplicating the node and edge rendering components.

## 9. How to implement

<Steps>
  <Step>
    ### Spot the varying algorithm
    Find the method or conditional block inside your Context class that changes frequently or supports multiple modes.
  </Step>
  <Step>
    ### Declare the Strategy interface
    Define a small contract (often one method, or a TypeScript function type) with only the inputs the algorithm needs.
  </Step>
  <Step>
    ### Extract Concrete Strategies
    Move each branch into its own class or function implementing the Strategy interface.
  </Step>
  <Step>
    ### Inject and delegate from the Context
    Store the Strategy reference on the Context (via constructor or setter) and delegate execution to it.
  </Step>
</Steps>

## 12. Check yourself

<MyTake>
In TypeScript, I start with a function type `(release: Release) => Promise<DeployResult>` when a strategy is stateless, and only promote it to a class implementing `DeployStrategy` when the strategy needs its own configuration fields (like `trafficPercent` or a metrics client).
</MyTake>
