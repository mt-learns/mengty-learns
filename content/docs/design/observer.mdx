## 1. Intent

<Intent>
Define a one-to-many subscription mechanism so a **Subject** (publisher) can notify an arbitrary, runtime-configurable list of **Observers** (subscribers) whenever an event occurs, without knowing their concrete types.
</Intent>

## 2. Problem

Imagine you run a CI build pipeline. When a build finishes or fails, you want to write a structured log line, increment Prometheus metrics, and send a Slack alert on failure.

If `BuildPipeline` imports `LogWriter`, `MetricsClient`, and `SlackWebhook` directly and calls each one inside `finishBuild()`, your core runner becomes coupled to every reporting tool. Adding a PagerDuty alert or disabling Slack in local dev requires editing `BuildPipeline` itself.

## 3. Solution

Give `BuildPipeline` a subscription list (`subscribe`, `unsubscribe`, `notify`) that only knows about a tiny `BuildObserver` interface (`onBuildEvent(event)`).

Each consumer (`LogSubscriber`, `MetricsSink`, `SlackNotifier`) implements `BuildObserver` and registers itself at startup—or detaches when no longer needed. When a stage completes, `BuildPipeline` simply loops over its active subscribers and calls `onBuildEvent(event)`.

### Observer vs Pub/Sub via a broker

People often use "Observer" and "Pub/Sub" interchangeably, but they operate at different boundaries:

| Aspect | Observer pattern | Pub/Sub (via broker) |
|---|---|---|
| **Coupling** | Subject holds direct references to Observer interfaces | Publisher and Subscriber never reference each other |
| **Delivery** | Usually synchronous, in-process method calls | Asynchronous over a broker (Redis, Kafka, RabbitMQ) |
| **Failure isolation** | A slow or throwing observer can block the subject | Broker buffers retries and dead-letter queues |

## 4. Real-world analogy

<Analogy>
Think of a CI/CD webhook registry on a Git repository. The repository does not know or care whether the listener is a Slack bot, a deploy trigger, or an audit logger—it just sends the same JSON payload to every registered endpoint when a push happens.
</Analogy>

## 7. Code

<Tabs items={['TypeScript']}>
  <Tab value="TypeScript">
```ts
type BuildStatus = 'started' | 'succeeded' | 'failed';

interface BuildEvent {
  pipelineId: string;
  status: BuildStatus;
  durationMs: number;
}

// Observer interface
interface BuildObserver {
  onBuildEvent(event: BuildEvent): void;
}

// Subject (Publisher)
class PipelineRunner {
  private readonly observers = new Set<BuildObserver>();

  subscribe(observer: BuildObserver): () => void {
    this.observers.add(observer);
    return () => {
      this.observers.delete(observer);
    };
  }

  run(pipelineId: string, shouldFail = false): void {
    this.notify({ pipelineId, status: 'started', durationMs: 0 });
    const status: BuildStatus = shouldFail ? 'failed' : 'succeeded';
    this.notify({ pipelineId, status, durationMs: 1420 });
  }

  private notify(event: BuildEvent): void {
    for (const observer of this.observers) {
      observer.onBuildEvent(event);
    }
  }
}

// Concrete Observers
class LogSubscriber implements BuildObserver {
  onBuildEvent(event: BuildEvent): void {
    console.log(`[log] ${event.pipelineId}: ${event.status} (${event.durationMs}ms)`);
  }
}

class MetricsSink implements BuildObserver {
  onBuildEvent(event: BuildEvent): void {
    if (event.status !== 'started') {
      console.log(`[metric] build_duration_ms{status="${event.status}"} ${event.durationMs}`);
    }
  }
}

class SlackNotifier implements BuildObserver {
  onBuildEvent(event: BuildEvent): void {
    if (event.status === 'failed') {
      console.log(`[slack] ALERT: ${event.pipelineId} failed`);
    }
  }
}

// Usage
const runner = new PipelineRunner();
runner.subscribe(new LogSubscriber());
runner.subscribe(new MetricsSink());
const unsubscribeSlack = runner.subscribe(new SlackNotifier());

runner.run('web-app-main', true);
unsubscribeSlack(); // clean detach when no longer needed
```

## 8. When to use / when to avoid

<Checklist
  use={[
    'A state change in one object must trigger updates in an unknown or dynamic set of other objects.',
    'Subscribers need to attach and detach at runtime (e.g. temporary debug loggers, UI components).',
    'You want core domain logic to emit facts without importing logging, metrics, or webhook clients.',
  ]}
  avoid={[
    'There is only one fixed consumer—a direct function call or injected callback is simpler and easier to trace.',
    'Subscriber execution order or transactional rollback is critical—Observer notifies in registration/arbitrary order.',
    'You need cross-service durability, retries, or backpressure—use a message broker (Pub/Sub) instead.',
  ]}
/>

### When NOT to use it

Overengineering happens when you wire an event emitter between two modules that always have a 1:1 relationship. Replacing a direct `metrics.record(duration)` call with an event bus makes stack traces harder to follow and hides which code actually runs when a method is called.

### Real-world example in this stack

In this site's diagram and flow components (`components/flow/` and `components/diagram/`), the browser's `IntersectionObserver` and `ResizeObserver` APIs notify the component when a `<Flow>` scrolls into view (triggering lazy-loading of React Flow) or when its container resizes (re-running `fitView`).

## 9. How to implement

<Steps>
  <Step>
    ### Separate core state from side effects
    Identify the Subject (`PipelineRunner`) whose state changes other modules care about.
  </Step>
  <Step>
    ### Define the Observer interface
    Declare a minimal notification method (`onBuildEvent(event)`) carrying the event payload.
  </Step>
  <Step>
    ### Add subscription management to the Subject
    Store observers in a `Set` and return an `unsubscribe()` cleanup closure from `subscribe()`.
  </Step>
  <Step>
    ### Register concrete observers at composition time
    Wire `LogSubscriber`, `MetricsSink`, and `SlackNotifier` at app startup rather than inside the Subject.
  </Step>
</Steps>

## 10. Pros / Cons

<ProsCons
  pros={[
    'Open/Closed Principle: add new subscribers without modifying the Subject.',

  ]}
  cons={[
    'Notification order is not guaranteed and cascading events can be hard to debug.',
    'Forgotten unsubscriptions cause memory leaks in long-lived processes.',

## 12. Check yourself

<MyTake>
Always return an `unsubscribe` function from `subscribe()`, and wrap each observer invocation in a `try/catch` if one failing telemetry sink must never crash a deployment or request path.
</MyTake>
