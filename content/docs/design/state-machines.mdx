## TL;DR
A **finite state machine** models an entity's lifecycle using mutually exclusive **states**, **events**, **guards**, and **actions**—making illegal transitions (like shipping a cancelled order) unrepresentable in code.

## 1. Intent

<Intent>
Make every valid lifecycle state and allowed transition explicit, so an entity can never enter an inconsistent state or skip required business checks.
</Intent>

## 2. Problem

When workflows start simple, teams often track lifecycle with loose boolean flags or nullable timestamps: `isSubmitted`, `isApproved`, `isCancelled`, `refundedAt`. With 4 booleans, there are $2^4 = 16$ possible combinations, even when only 5 are valid.

Without an explicit transition table, every endpoint has to remember which flags to check. One missed `if (order.isCancelled)` check allows a refund on an unpaid order or a deploy promotion after a rollback has started.

## 3. Solution

Replace loose flags with a single **state** field and an explicit **transition function** `(currentState, event) -> nextState`:

- **State**: One mutually exclusive condition (`Draft`, `Issued`, `Paid`, `Cancelled`, `Refunded`).
- **Event**: The command or external signal (`issue`, `pay`, `cancel`, `refund`).
- **Guard**: A precondition that must hold before the transition fires (e.g., `amount > 0` or `actor.role === 'manager'`).
- **Action**: Side effects tied to the transition (e.g., emit audit event, release reserved stock).
- **Terminal state**: A final state (`Refunded`, `Discarded`) with no outgoing transitions.

## 4. Real-world analogy

<Analogy>
Think of a CI/CD deployment pipeline. A release cannot jump directly from `Queued` to `Promoted` without passing `Building` and `Verified`. Each gate (tests passing, manual approval) acts as a **guard**, and once a release is `RolledBack`, it cannot be `Promoted` again—you must start a new release.
</Analogy>

## 7. Code

```ts
export type OrderState =
  | { status: 'draft'; items: string[] }
  | { status: 'issued'; items: string[]; issuedAt: string }
  | { status: 'paid'; items: string[]; paidAt: string; receiptId: string }
  | { status: 'cancelled'; reason: string }
  | { status: 'refunded'; receiptId: string; refundedAt: string };

export type OrderEvent =
  | { type: 'ISSUE'; now: string }
  | { type: 'PAY'; receiptId: string; now: string }
  | { type: 'CANCEL'; reason: string }
  | { type: 'REFUND'; approvedByManager: boolean; now: string };

export function transitionOrder(state: OrderState, event: OrderEvent): OrderState {
  switch (state.status) {
    case 'draft':
      if (event.type === 'ISSUE') {
        if (state.items.length === 0) {
          throw new Error('Guard failed: cannot issue an empty order');
        }
        return { status: 'issued', items: state.items, issuedAt: event.now };
      }
      if (event.type === 'CANCEL') {
        return { status: 'cancelled', reason: event.reason };
      }
      break;

    case 'issued':
      if (event.type === 'PAY') {
        return {
          status: 'paid',
          items: state.items,
          paidAt: event.now,
          receiptId: event.receiptId,
        };
      }
      if (event.type === 'CANCEL') {
        return { status: 'cancelled', reason: event.reason };
      }
      break;

    case 'paid':
      if (event.type === 'REFUND') {
        if (!event.approvedByManager) {
          throw new Error('Guard failed: manager approval required for refund');
        }
        return {
          status: 'refunded',
          receiptId: state.receiptId,
          refundedAt: event.now,
        };
      }
      break;

    case 'cancelled':
    case 'refunded':
      throw new Error(`Terminal state '${state.status}' rejects event '${event.type}'`);

    default: {
      const _exhaustive: never = state;
      return _exhaustive;
    }
  }

  throw new Error(`Invalid transition: '${state.status}' cannot handle '${event.type}'`);
}
```

## 8. When to use / when to avoid

<Checklist
  use={[
    "Entities with 3 or more lifecycle phases where order matters (orders, invoices, deployments, tickets).",
    "Workflows with strict regulatory or financial invariants (e.g. cannot refund before payment).",
    "Distributed workflows where retries or duplicate webhooks could otherwise re-run a step.",
  ]}
  avoid={[
    "Simple CRUD records that only have an active/archived toggle.",
    "Purely stateless calculations where no history or phase restricts the next operation.",
  ]}
/>

## 9. How to implement

<Steps>
  <Step>
    ### List all valid states
    Identify every mutually exclusive lifecycle phase and mark terminal states (`cancelled`, `refunded`).
  </Step>
  <Step>
    ### List all events
    Define every command or external signal that can act on the entity (`ISSUE`, `PAY`, `CANCEL`, `REFUND`).
  </Step>
  <Step>
    ### Build the transition function
    Map `(state, event) -> nextState` using a discriminated union `switch` with an exhaustive `never` check.
  </Step>
  <Step>
    ### Add guards and idempotent side effects
    Validate permissions, invariants, and idempotency keys before mutating state or emitting events.
  </Step>
  <Step>
    ### Test valid and invalid transitions
    Write unit tests for every legal move, rejected move, and terminal state.
  </Step>
</Steps>
