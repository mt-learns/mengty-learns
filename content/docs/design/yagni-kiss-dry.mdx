## TL;DR
**YAGNI** keeps you from building for imaginary futures, **KISS** favors code the next engineer can read without a tour, and **DRY** means **one source of truth for a business rule**—never blindly merging two functions just because their syntax looks alike today.

## Why it exists
Duplication is visible and cheap to fix later. A **wrong abstraction** is invisible and expensive to undo because every caller has already coupled to it—forcing future requirements through boolean flags and escape-hatch maps.

## Mental model
Before merging two similar code blocks, ask: *"If rule A changes tomorrow, must rule B change identically?"*

## Do it

### 1. YAGNI (You Aren't Gonna Need It)
Build for the requirement you have. Adding flexibility *after* a second real requirement arrives is usually cheaper than guessing upfront, because by then you know what actually varies.

### 2. KISS (Keep It Simple, Stupid)
"Simple" does not mean clever or terse—it means the next engineer can trace the behavior in two minutes without decoding a custom YAML rules engine or five layers of generics.

### 3. The Two Kinds of DRY (Don't Repeat Yourself)
- **False DRY (merging by shape):** Two email validators—one for public signups and one for internal staff—happen to share the same regex today. Merging them into `validateEmail(email, { requireCorpDomain?: boolean })` couples unrelated rules. When staff rules change, every caller has to inspect flags.
- **Genuine DRY (single source of truth):** A validation schema shared between frontend form and backend API ensures they never drift.

```ts
import { z } from 'zod';

// Genuine DRY: one schema shared by client form and server handler
export const deployRequestSchema = z.object({
  service: z.string().min(2),
  environment: z.enum(['staging', 'production']),
  replicas: z.number().int().min(1).max(20),
});

export type DeployRequest = z.infer<typeof deployRequestSchema>;
```

```ts
// False DRY avoided: shared regex constant, separate business rules
const EMAIL_FORMAT = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;

export function isValidPublicEmail(email: string): boolean {
  return EMAIL_FORMAT.test(email);
}

export function isValidStaffEmail(email: string, allowedDomains: readonly string[]): boolean {
  if (!EMAIL_FORMAT.test(email)) return false;
  const domain = email.split('@')[1]?.toLowerCase();
  return domain !== undefined && allowedDomains.includes(domain);
}
```

## Gotchas
- **Flag-parameter creep:** A shared helper accumulating `isAdmin`, `skipCheck`, or `mode` flags is a sign of false DRY—split it back into two explicit functions.
- **Abstracting on case #1:** Creating `BaseNotifier` + `NotifierFactory` when you only send Slack messages locks in the wrong interface before you know what email or PagerDuty actually need.
- **Using YAGNI as an excuse to skip fundamentals:** YAGNI applies to speculative features, *not* to input validation, auth checks, or parameterized SQL.

## Production checklist
- [ ] Apply the **Rule of Three**: duplicate once, note it twice, abstract on the third real case.
- [ ] Keep shared validation schemas, status enums, and API contracts in one source of truth (genuine DRY).
- [ ] Split shared helpers that accumulate boolean mode flags for different callers.
- [ ] Prefer explicit, readable functions over clever generic frameworks.
