## TL;DR
An **anti-pattern** is a tempting shortcut or over-engineered structure that feels productive at first but slows every future change. Spot the big ones—**God Service**, **Speculative Generality**, **Golden Hammer**, and **Distributed Monolith**—and refactor them incrementally instead of attempting a big-bang rewrite.

## Why it exists
Anti-patterns rarely come from carelessness. They usually appear when teams either **skip boundaries** under deadline pressure (creating a God Service or Big Ball of Mud) or **over-apply patterns** after reading a book (creating 17 files of single-implementation interfaces to save one record).

## Mental model
Every design choice trades **indirection** against **coupling**. Too little structure creates tangles; too much unmotivated structure creates maze-like indirection.

## Do it

### Common anti-patterns and their fixes

| Anti-pattern | Symptom in the codebase | Root cause | Practical fix |
|---|---|---|---|
| **God Object / God Service** | One 2,000-line class owns billing, auth, notifications, and exports | New features kept getting appended to the nearest service | Extract one cohesive responsibility at a time behind a narrow function or module |
| **Speculative Generality** | 30+ interfaces with exactly one `Default*` implementation each | Designing for hypothetical future variants ("for testability") | Inline single-use abstractions; wait for the third real variant before abstracting |
| **Spaghetti Code** | Deep `if/else` nesting, hidden side effects, global state mutations | Missing pure functions and early returns | Flatten with guard clauses, isolate I/O at the edges |
| **Golden Hammer** | Every problem solved with the same hammer (e.g. Kafka or microservices for a 2-table CRUD app) | Familiarity bias instead of fitness for purpose | Write a short ADR comparing the boring default against the specialized tool |
| **Distributed Monolith** | 12 microservices that must all deploy together or share one database | Splitting by technical layer instead of bounded context | Merge tightly coupled services back into a modular monolith or decouple via async contracts |
| **Premature Optimization** | Custom bit-packing or hand-rolled caches with zero profiling data | Optimizing guessed bottlenecks | Measure with a profiler or benchmark first; optimize only the measured hot path |

### Concrete tell: single-implementation interfaces
You don't need a complex static analyzer to spot speculative generality. In a TypeScript or Java codebase, look for interfaces that only have one production class implementing them (excluding genuine external-port seams like payment gateways or databases).

```ts
// Anti-pattern: 4 layers of indirection for 1 implementation
interface OrderIntakeStrategy {
  execute(input: CreateOrderInput): Promise<string>;
}
class DefaultOrderIntakeStrategy implements OrderIntakeStrategy {
  async execute(input: CreateOrderInput): Promise<string> {
    return saveOrder(input);
  }
}

// Clearer: plain function or single service until a real second variant arrives
export async function createOrder(
  repo: OrderRepo,
  input: CreateOrderInput,
): Promise<string> {
  return repo.save(input);
}
```

### Incremental recovery plan
1. **Measure the pain:** track lead time for small changes, bug hotspots, and onboarding time.
2. **Wrap with characterization tests** around the messy boundary before moving code.
3. **Refactor one seam per PR**—never freeze feature delivery for a multi-month rewrite.

## Gotchas
- **Deleting abstractions without tests:** Inlining a 5-deep decorator stack without checking what each layer did can silently drop audit logging or validation.
- **Replacing a Monolith with a Distributed Monolith:** Splitting code over HTTP without decoupling data ownership makes incidents harder to debug, not easier.
- **Confusing "clean" with "more files":** Splitting a 60-line module into 8 files of one-line interfaces lowers readability.

## Production checklist
- [ ] Review PRs for single-implementation interfaces that have no second variant on the roadmap.
- [ ] Check service boundaries: if two services always deploy together, they belong in one deployable unit.
- [ ] Require profiling or latency metrics before accepting complex caching or concurrency optimizations.
- [ ] Schedule incremental debt paydown alongside feature work instead of waiting for a rewrite.
