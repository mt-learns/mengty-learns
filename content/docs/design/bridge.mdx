## 1. Intent

<Intent>
Split a large class or tightly coupled hierarchy into two independent hierarchies—**Abstraction** and **Implementation**—connected by composition instead of inheritance, so each side can vary without multiplying subclasses.
</Intent>

## 2. Problem

Suppose you are building a remote control library for smart devices. You start with a `RemoteControl` base class and subclass it for each device: `TVRemote` and `RadioRemote`. Then you add an `AdvancedRemote` with mute and voice controls. Suddenly you need `AdvancedTVRemote` and `AdvancedRadioRemote`.

Every new remote type or new device multiplies the class count (`M remotes × N devices`). Adding a third device means writing two more remote subclasses; adding a third remote style means writing three more.

## 3. Solution

Instead of inheriting from every combination, extract the **device** operations into an interface (`Device`) and give `RemoteControl` a reference to a `Device` instance.

- The **Abstraction** (`RemoteControl`, `AdvancedRemote`) handles user-facing controls like `togglePower()` or `mute()`.
- The **Implementation** (`Device`, implemented by `TV` and `Radio`) handles low-level state like `enable()`, `disable()`, and `setVolume()`.

The reference from `RemoteControl` to `Device` is the **bridge**. Now you can add new remotes or new devices independently (`M + N` classes instead of `M × N`).

## 4. Real-world analogy

<Analogy>
Think of a universal remote and a TV. The remote's buttons (Power, Volume Up, Mute) are the **abstraction**. The infrared receiver inside your Sony TV or Bose radio is the **implementation**. You can upgrade to a touchscreen remote without rewiring your TV, and you can swap your TV without relearning the remote's layout.
</Analogy>

## 7. Code

<Tabs items={['TypeScript']}>
  <Tab value="TypeScript">
```ts
// Implementation interface
interface Device {
  isEnabled(): boolean;
  enable(): void;
  disable(): void;
  getVolume(): number;
  setVolume(percent: number): void;
}

// Concrete Implementations
class TV implements Device {
  private on = false;
  private volume = 30;

  isEnabled() { return this.on; }
  enable() { this.on = true; }
  disable() { this.on = false; }
  getVolume() { return this.volume; }
  setVolume(percent: number) {
    this.volume = Math.max(0, Math.min(100, percent));
  }
}

class Radio implements Device {
  private on = false;
  private volume = 15;

  isEnabled() { return this.on; }
  enable() { this.on = true; }
  disable() { this.on = false; }
  getVolume() { return this.volume; }
  setVolume(percent: number) {
    this.volume = Math.max(0, Math.min(100, percent));
  }
}

// Abstraction
class RemoteControl {
  constructor(protected readonly device: Device) {}

  togglePower(): void {
    if (this.device.isEnabled()) {
      this.device.disable();
    } else {
      this.device.enable();
    }
  }

  volumeUp(): void {
    this.device.setVolume(this.device.getVolume() + 10);
  }
}

// Refined Abstraction
class AdvancedRemote extends RemoteControl {
  mute(): void {
    this.device.setVolume(0);
  }
}

// Usage
const tvRemote = new RemoteControl(new TV());
tvRemote.togglePower();

const radioRemote = new AdvancedRemote(new Radio());
radioRemote.togglePower();
radioRemote.mute();
```

## 8. When to use / when to avoid

<Checklist
  use={[
    'You have two orthogonal dimensions that vary independently (e.g. UI controls × platform APIs, or shapes × renderers).',
    'You want to switch implementations at runtime without changing client code.',
    'A monolithic class is growing too large because it mixes high-level logic with platform-specific details.',
  ]}
  avoid={[
    'There is only one implementation and no realistic plan to add another.',
    'The abstraction and implementation are tightly bound by performance or lifecycle constraints.',
    'A simple function callback or Strategy would solve the variation with less boilerplate.',
  ]}
/>

## 9. How to implement

<Steps>
  <Step>
    ### Identify the two independent dimensions
    Separate what the caller interacts with (**Abstraction**) from the low-level work (**Implementation**).
  </Step>
  <Step>
    ### Define the Implementor interface
    Keep it focused on primitive operations (`enable`, `disable`, `setVolume`) rather than high-level workflows.
  </Step>
  <Step>
    ### Store the Implementor on the Abstraction
    Inject the `Device` via the `RemoteControl` constructor and delegate work to it.
  </Step>
  <Step>
    ### Extend either side independently
    Add `AdvancedRemote` without touching `TV` or `Radio`, and add `Projector` without touching any remote class.
  </Step>
</Steps>

## 10. Pros / Cons

<ProsCons
  pros={[
    'Prevents M × N subclass explosion when two dimensions grow.',
    'Follows Open/Closed Principle: add new abstractions or implementations without modifying existing ones.',
    'Keeps platform-specific details isolated behind a clean interface.',
  ]}
  cons={[
    'Adds extra indirection and interfaces, which is overkill for simple hierarchies.',
    'Harder to read at a glance if both sides are over-abstracted too early.',
  ]}
/>

## 12. Check yourself

<MyTake>
In TypeScript codebases, I reach for Bridge when I catch myself naming classes like `PostgresOrderExporter` and `CsvOrderExporter` alongside `AsyncPostgresOrderExporter`. Splitting `Exporter` (sync/async) from `StorageDriver` (Postgres/CSV) immediately stops the combinatorial growth.
</MyTake>
