## 1. Intent

<Intent>
Split a large class or tightly coupled hierarchy into two independent hierarchies—**Abstraction** and **Implementation**—connected by composition instead of inheritance, so each side can vary without multiplying subclasses.
</Intent>

## 2. Problem

Suppose you are building an order-export module. You start with an `OrderExporter` base class and subclass it per backend: `PostgresOrderExporter` and `CsvOrderExporter`. Next, you need an `AsyncOrderExporter` that batches writes and retries transient errors. Suddenly you need `AsyncPostgresOrderExporter` and `AsyncCsvOrderExporter`.

Every new exporter mode or storage backend multiplies the class count (`M exporters × N drivers`). Adding a third storage driver (say S3) means writing two more exporter subclasses; adding a third exporter mode means writing three more.

## 3. Solution

Instead of inheriting from every combination, extract the **storage** operations into an interface (`StorageDriver`) and give `OrderExporter` a reference to a `StorageDriver` instance.

- The **Abstraction** (`OrderExporter`, `AsyncExporter`) handles export orchestration like formatting payloads, batching, or retrying.
- The **Implementation** (`StorageDriver`, implemented by `PostgresDriver` and `CsvDriver`) handles low-level I/O like `connect()`, `writeRecord()`, and `close()`.

The reference from `OrderExporter` to `StorageDriver` is the **bridge**. Now you can add new exporters or new storage drivers independently (`M + N` classes instead of `M × N`).

## 4. Real-world analogy

<Analogy>
Think of a shipping-label generator and a printer. The generator's layout rules (standard label, customs form) are the **abstraction**. The physical printer driver (Zebra thermal, PDF file) is the **implementation**. You can add a new customs-form layout without rewriting printer drivers, and you can swap to a new printer without changing label layouts.
</Analogy>

## 7. Code

<Tabs items={['TypeScript']}>
  <Tab value="TypeScript">
```ts
// Implementation interface
interface StorageDriver {
  connect(): Promise<void>;
  writeRecord(collection: string, record: Record<string, unknown>): Promise<string>;
  close(): Promise<void>;
}

// Concrete Implementations
class PostgresDriver implements StorageDriver {
  async connect() { /* open connection pool */ }
  async writeRecord(collection: string, record: Record<string, unknown>) {
    return `pg:${collection}:${String(record.id ?? 'new')}`;
  }
  async close() { /* drain pool */ }
}

class CsvDriver implements StorageDriver {
  private rows: string[] = [];
  async connect() { this.rows = []; }
  async writeRecord(_collection: string, record: Record<string, unknown>) {
    this.rows.push(JSON.stringify(record));
    return `csv:row-${this.rows.length}`;
  }
  async close() { /* flush file handle */ }
}

// Abstraction
class OrderExporter {
  constructor(protected readonly driver: StorageDriver) {}

  async exportOrder(order: { id: string; totalCents: number }): Promise<string> {
    await this.driver.connect();
    const receipt = await this.driver.writeRecord('orders', order);
    await this.driver.close();
    return receipt;
  }
}

// Refined Abstraction
class AsyncExporter extends OrderExporter {
  async exportBatch(orders: { id: string; totalCents: number }[]): Promise<string[]> {
    await this.driver.connect();
    const receipts = await Promise.all(
      orders.map((order) => this.driver.writeRecord('orders', order)),
    );
    await this.driver.close();
    return receipts;
  }
}

// Usage
const pgExporter = new OrderExporter(new PostgresDriver());
await pgExporter.exportOrder({ id: 'ord_1', totalCents: 2500 });

const csvBatch = new AsyncExporter(new CsvDriver());
await csvBatch.exportBatch([
  { id: 'ord_2', totalCents: 1200 },
  { id: 'ord_3', totalCents: 4900 },
]);
```

## 8. When to use / when to avoid

<Checklist
  use={[
    'You have two orthogonal dimensions that vary independently (e.g. UI controls × platform APIs, or shapes × renderers).',
    'You want to switch implementations at runtime without changing client code.',
    'A monolithic class is growing too large because it mixes high-level logic with platform-specific details.',
  ]}
  avoid={[
    'There is only one implementation and no realistic plan to add another.',
    'The abstraction and implementation are tightly bound by performance or lifecycle constraints.',
    'A simple function callback or Strategy would solve the variation with less boilerplate.',
  ]}
/>

## 9. How to implement

<Steps>
  <Step>
    ### Identify the two independent dimensions
    Separate what the caller interacts with (**Abstraction**) from the low-level work (**Implementation**).
  </Step>
  <Step>
    ### Define the Implementor interface
    Keep it focused on primitive operations (`connect`, `writeRecord`, `close`) rather than high-level workflows.
  </Step>
  <Step>
    ### Store the Implementor on the Abstraction
    Inject the `StorageDriver` via the `OrderExporter` constructor and delegate work to it.
  </Step>
  <Step>
    ### Extend either side independently
    Add `AsyncExporter` without touching `PostgresDriver` or `CsvDriver`, and add `S3Driver` without touching any exporter class.
  </Step>
</Steps>

## 10. Pros / Cons

<ProsCons
  pros={[
    'Prevents M × N subclass explosion when two dimensions grow.',
    'Follows Open/Closed Principle: add new abstractions or implementations without modifying existing ones.',
    'Keeps platform-specific details isolated behind a clean interface.',
  ]}
  cons={[
    'Adds extra indirection and interfaces, which is overkill for simple hierarchies.',
    'Harder to read at a glance if both sides are over-abstracted too early.',
  ]}

## 12. Check yourself

<MyTake>
In TypeScript codebases, I reach for Bridge when I catch myself naming classes like `PostgresOrderExporter` and `CsvOrderExporter` alongside `AsyncPostgresOrderExporter`. Splitting `Exporter` (sync/async) from `StorageDriver` (Postgres/CSV) immediately stops the combinatorial growth.
</MyTake>
