## TL;DR
The **Mediator** pattern replaces a tangled web of direct component-to-component calls with a single **coordinator** that orchestrates the workflow while keeping domain rules inside each component.

## 1. Intent

<Intent>
Reduce chaotic dependencies between collaborating objects by forcing them to communicate only through a central **Mediator** object.
</Intent>

## 2. Problem

Imagine a release-promotion workflow in a platform service. Four components need to cooperate: `ArtifactRegistry` (verifies image digest), `HealthProbe` (checks staging readiness), `TrafficRouter` (shifts production weight), and `IncidentNotifier` (posts to chat).

If each component calls the others directly—`HealthProbe` tells `TrafficRouter` to shift traffic and tells `IncidentNotifier` to alert on failure, while `TrafficRouter` asks `ArtifactRegistry` for metadata—every component becomes coupled to three others. Changing one signature breaks callers across the module, and testing any component requires mocking its neighbors.

## 3. Solution

Extract the coordination logic into a **Mediator** (for example, `ReleaseMediator`). Each colleague component only depends on a minimal `Mediator` interface—or is invoked directly by the Mediator—and never holds references to other colleagues.

Colleagues stay focused on their own responsibility (verifying a digest, checking `/healthz`, shifting traffic, sending a message), while the Mediator owns only the sequence and error handling between them.

## 4. Real-world analogy

<Analogy>
Think of an **air traffic control tower**. Aircraft do not negotiate landing slots directly with every other plane in the sky—that would be a catastrophic many-to-many protocol. Instead, each pilot communicates only with the tower (the Mediator), which sequences takeoffs and landings safely.
</Analogy>

## 7. Code

```ts
export interface Mediator {
  notify(sender: string, event: 'staging_ready' | 'staging_failed'): Promise<void>;
}

export class HealthProbe {
  constructor(private mediator: Mediator) {}

  async check(releaseId: string, healthy: boolean): Promise<void> {
    if (healthy) {
      await this.mediator.notify('HealthProbe', 'staging_ready');
    } else {
      await this.mediator.notify('HealthProbe', 'staging_failed');
    }
  }
}

export class TrafficRouter {
  async shiftTo(weight: number): Promise<string> {
    return `Traffic shifted to ${weight}%`;
  }
}

export class AlertNotifier {
  async send(message: string): Promise<void> {
    console.log(`[ALERT] ${message}`);
  }
}

export class ReleaseMediator implements Mediator {
  constructor(
    private router: TrafficRouter,
    private notifier: AlertNotifier,
  ) {}

  async notify(sender: string, event: 'staging_ready' | 'staging_failed'): Promise<void> {
    if (sender === 'HealthProbe' && event === 'staging_ready') {
      const status = await this.router.shiftTo(100);
      await this.notifier.send(status);
      return;
    }

    if (event === 'staging_failed') {
      await this.router.shiftTo(0);
      await this.notifier.send('Promotion aborted: staging probe failed');
    }
  }
}
```

## 8. When to use / when to avoid

<Checklist
  use={[
    "Several components communicate in complex ways, forming a tightly coupled dependency web.",
    "You want to reuse a component (like HealthProbe or TrafficRouter) in another workflow without dragging its neighbors along.",
    "A use case spans multiple services and needs explicit ordering or compensation on failure.",
  ]}
  avoid={[
    "Only two components talk to each other—direct method calls or a simple callback are clearer.",
    "Components only need fire-and-forget broadcast notifications (use Observer or an event bus instead).",
  ]}
/>

## 9. How to implement

<Steps>
  <Step>
    ### Identify the coupled group
    Find components that currently hold direct references to one another.
  </Step>
  <Step>
    ### Declare the Mediator interface
    Define a focused coordination contract (such as `notify(sender, event)` or a use-case command).
  </Step>
  <Step>
    ### Remove direct sibling references
    Inject the Mediator into each colleague so colleagues never import each other.
  </Step>
  <Step>
    ### Keep domain rules in colleagues
    Let the Mediator own only workflow ordering, transactions, or compensating rollbacks.
  </Step>
  <Step>
    ### Test colleagues and Mediator separately
    Unit test each colleague in isolation, then test happy and failure paths on the Mediator.
  </Step>
</Steps>
