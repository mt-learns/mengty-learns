## TL;DR
**Rate limiting** caps request rates per key (**IP**, **user ID**, **API token**, or **email**) to stop brute force, credential stuffing, and resource exhaustion. Use **Token Bucket** for controlled bursts or **Sliding Window** for smooth limits, enforce coarse limits at the **edge** and business limits in the **app**, and return **`429 Too Many Requests`** with **`Retry-After`**.

## Intent
<Intent>
Pick the right rate-limiting algorithm and key, place enforcement at both the edge and application layers, and signal backoff cleanly with `429` + `Retry-After`.
</Intent>

## Problem
Without rate limits, an attacker can run millions of password guesses against `/login`, exhaust DB connections with expensive search queries, or rack up third-party SMS/AI bills. Conversely, a naive IP-only fixed-window limit can block an entire office behind one NAT IP or allow 2× bursts at minute boundaries.

## Solution
Combine the right algorithm, key, and enforcement point:

| Algorithm | How it works | Best for |
|---|---|---|
| **Fixed Window** | Counter resets every $N$ seconds. | Simple coarse quotas (beware 2× boundary bursts). |
| **Sliding Window** | Weighted or rolling log over the last $N$ seconds. | Smooth API quotas with no boundary spikes. |
| **Token Bucket** | Bucket holds up to $B$ tokens, refilling at $R$/sec; each request consumes 1 (or $cost$) tokens. | Legitimate UI bursts (loading a dashboard) with a steady average rate. |

- **Keys:** Key unauthenticated routes by **client IP** (from a trusted proxy header, never a spoofable `X-Forwarded-For` from untrusted clients), login/reset routes by **IP + normalized account identifier**, and authenticated APIs by **user ID / API key**.
- **Response:** Return `429 Too Many Requests` with `Retry-After: <seconds>` so well-behaved clients back off instead of retrying in a tight loop.

## Real-world analogy
<Analogy>
A **Token Bucket** is a coffee punch card that automatically gains 1 stamp every 10 seconds up to a maximum of 5 stamps. You can order 5 coffees back-to-back in a burst, then you must wait 10 seconds per coffee—preventing anyone from monopolizing the espresso machine.
</Analogy>

## Code
An in-memory token bucket (suitable for single-instance demos; use atomic Redis Lua scripts in multi-instance production):

```ts
// SAFE: token bucket with explicit capacity, refill rate, and Retry-After calculation
type Bucket = { tokens: number; updatedAt: number };
const buckets = new Map<string, Bucket>();

export function checkTokenBucket(
  key: string,
  capacity = 5,
  refillPerSec = 0.5,
  now = Date.now(),
): { allowed: boolean; retryAfterSec: number } {
  const b = buckets.get(key) ?? { tokens: capacity, updatedAt: now };
  const elapsedSec = Math.max(0, (now - b.updatedAt) / 1000);
  const tokens = Math.min(capacity, b.tokens + elapsedSec * refillPerSec);

  if (tokens < 1) {
    buckets.set(key, { tokens, updatedAt: now });
    return { allowed: false, retryAfterSec: Math.ceil((1 - tokens) / refillPerSec) };
  }

  buckets.set(key, { tokens: tokens - 1, updatedAt: now });
  return { allowed: true, retryAfterSec: 0 };
}
```

## How to implement
<Steps>
  <Step>
    ### Configure edge limits first
    Enable Cloudflare/WAF/Nginx rate-limiting rules to drop volumetric floods at the perimeter.
  </Step>
  <Step>
    ### Add route-specific app limits
    Apply tighter token-bucket or sliding-window limits on `/login`, `/forgot-password`, and `/api/export`.
  </Step>
  <Step>
    ### Emit 429 and monitor spikes
    Return `429 Too Many Requests` with `Retry-After` and alert on sustained 429 surges.
  </Step>
</Steps>
