## TL;DR
Centralizing SSO does not mean every app shares one token. Validate JWTs **locally via cached JWKS** with strict **`aud` checks**, use **RFC 8693 Token Exchange** to narrow audience/scope across trust boundaries, implement **back-channel logout**, and treat your IdP as **Tier-0 HA infrastructure**.

## 1. Intent

<Intent>
Provide seamless single sign-on across multiple applications while isolating token blast radius per service and keeping APIs resilient during IdP maintenance.
</Intent>

## 2. Problem

When organizations consolidate 5–10 apps onto one Identity Provider (IdP), three operational flaws often hide underneath:
1. **Shared audience:** Every API accepts any valid token from the realm without checking `aud`, so a low-privilege reporting app token can call a payment or admin API.
2. **Unbounded token forwarding:** Internal services forward the user's full-scope token across 4 hops, turning one compromised pod into full lateral access.
3. **Single-point-of-failure IdP:** Fetching JWKS per request or running a single IdP database instance causes a total outage whenever the IdP fails over.

## 3. Solution

Combine four controls:
1. **Local JWKS validation + strict `aud`:** Every resource server caches the IdP's JWKS keys and rejects any token whose `aud` does not match its own `client_id`.
2. **Short access-token lifetimes (3–5 min):** Bounds the window after revocation.
3. **Token Exchange (RFC 8693):** Before crossing a trust boundary, Service A exchanges the incoming token for a down-scoped token (`aud: service-b`, minimal `scope`) while keeping `sub` for the audit trail.
4. **Back-channel logout + HA IdP:** Server-to-server logout notifications revoke BFF sessions; IdP runs multi-AZ with a circuit breaker and quarterly failover drills.

## 4. Real-world analogy

<Analogy>
Think of **visitor badges at a secure campus**. At reception (**the IdP**), you show your passport once to prove who you are (**SSO session**). To enter the server room, reception issues a temporary badge valid *only* for Door B for 15 minutes (**Token Exchange**)—if someone steals that badge, it still cannot open the finance vault.
</Analogy>

## 7. Code

```ts
// RFC 8693 Token Exchange from Service A -> Service B
export async function exchangeToken(params: {
  tokenEndpoint: string;
  clientId: string;
  clientSecret: string;
  subjectToken: string;
  targetAudience: string;
  scope: string;
}): Promise<string> {
  const body = new URLSearchParams({
    grant_type: 'urn:ietf:params:oauth:grant-type:token-exchange',
    client_id: params.clientId,
    client_secret: params.clientSecret,
    subject_token: params.subjectToken,
    subject_token_type: 'urn:ietf:params:oauth:token-type:access_token',
    audience: params.targetAudience,
    scope: params.scope,
  });

  const res = await fetch(params.tokenEndpoint, {
    method: 'POST',
    headers: { 'content-type': 'application/x-www-form-urlencoded' },
    body,
    signal: AbortSignal.timeout(2000),
  });

  if (!res.ok) throw new Error(`Token exchange failed: ${res.status}`);
  const data = (await res.json()) as { access_token: string };
  return data.access_token;
}
```

## 9. How to implement

<Steps>
  <Step>
    ### Configure per-service clients and audiences
    Ensure every backend API has its own client ID and audience mapper in Keycloak.
  </Step>
  <Step>
    ### Enforce local JWKS + audience validation
    Cache JWKS keys with a 2-second timeout on refresh and reject mismatched `aud` claims.
  </Step>
  <Step>
    ### Enable Token Exchange for cross-boundary hops
    Exchange incoming tokens for narrow downstream tokens instead of forwarding broad tokens.
  </Step>
  <Step>
    ### Wire back-channel logout and HA failover tests
    Configure back-channel logout URLs on BFF clients and run regular IdP failover drills.
  </Step>
</Steps>
