## TL;DR
Use **one Keycloak realm per isolated user population** (never per environment), register **one client per frontend and one per backend API**, put API permissions in **client roles** (not global realm roles), and bundle job functions using **groups + composite roles**.

## 1. Intent

<Intent>
Structure Keycloak's identity model so permissions stay scoped per API, access tokens remain compact, and onboarding or auditing a team takes one group assignment.
</Intent>

## 2. Problem

Teams new to Keycloak often put everyone and everything into a single realm, one shared client, and flat realm roles like `admin` or `viewer`. Within a year, three problems appear:
1. **Role collisions:** Both `billing-api` and `docs-api` want a `viewer` role, so granting `viewer` accidentally opens both services.
2. **Token bloat:** Every user carries dozens of unrelated roles in every JWT.
3. **Policy lock-in:** External partners and internal employees share one realm, making separate password policies, themes, or IdPs impossible.

## 3. Solution

Map Keycloak primitives cleanly to your system boundaries:

| Primitive | Purpose | Design rule |
|---|---|---|
| **Realm** | Hard security boundary (users, keys, policies, IdPs) | One per user population (e.g. `staff` vs `partners`), **never** per environment |
| **Client** | Registered app or API | One public client per SPA/mobile app; one confidential/bearer client per backend API |
| **Client Role** | Permission scoped to one API (`billing.read`) | Default for all API authorization checks |
| **Realm Role** | Org-wide identity (`employee`, `platform-admin`) | Reserve strictly for cross-cutting identity tags |
| **Group + Composite** | Team or org structure + role bundle | Attach composite roles to groups for 1-click onboarding and clean audits |
| **Client Scope / Mapper** | Controls claims emitted per token | Keep JWTs minimal; emit only needed audience and roles |

## 4. Real-world analogy

<Analogy>
Think of a **multi-tenant office building**. Different companies have separate building entrances and security desks (**Realms**). Each floor's locked suite is a **Client** with its own keycard permissions (**Client Roles**), while an employee's job title (**Group + Composite Role**) grants the exact set of suite keys needed on day one.
</Analogy>

## 7. Code

When your resource server verifies a Keycloak JWT, read `resource_access[clientId].roles` (and validate `aud` / `iss`) instead of trusting global realm roles:

```ts
export interface KeycloakJwtPayload {
  sub: string;
  iss: string;
  aud: string | string[];
  resource_access?: Record<string, { roles?: string[] }>;
}

export function extractClientRoles(
  payload: KeycloakJwtPayload,
  clientId: string,
  expectedIssuer: string,
): Set<string> {
  if (payload.iss !== expectedIssuer) {
    throw new Error('Untrusted token issuer');
  }

  const audiences = Array.isArray(payload.aud) ? payload.aud : [payload.aud];
  if (!audiences.includes(clientId)) {
    throw new Error(`Token audience missing ${clientId}`);
  }

  const roles = payload.resource_access?.[clientId]?.roles ?? [];
  return new Set(roles);
}
```

## 9. How to implement

<Steps>
  <Step>
    ### Provision realms per user population
    Deploy separate Keycloak instances per environment, with one realm per distinct user group.
  </Step>
  <Step>
    ### Register frontend and API clients
    Create public PKCE clients for SPAs and confidential/bearer clients for each resource server.
  </Step>
  <Step>
    ### Define client roles per API
    Name permissions consistently (`orders.read`, `orders.write`) inside each API client.
  </Step>
  <Step>
    ### Bundle roles into groups via composite roles
    Assign composite roles to Groups so user onboarding and periodic access reviews stay simple.
  </Step>
</Steps>
