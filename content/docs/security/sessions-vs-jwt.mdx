## TL;DR
**Opaque server sessions** give instant revocation and simple security, while **stateless JWTs** avoid a central lookup per request at the cost of harder revocation. In browsers, store credentials in **`HttpOnly; Secure; SameSite` cookies** (never `localStorage`), keep access tokens short-lived, and rotate refresh tokens with **reuse detection**.

## Intent
<Intent>
Choose between opaque server sessions and JWT access tokens, design a safe refresh-token rotation lifecycle, and avoid the classic `alg: none`, key-confusion, and `localStorage` mistakes.
</Intent>

## Problem
Many apps issue 7-day JWTs stored in `localStorage` because "JWTs are modern and stateless". When a user logs out, changes their password, or gets hit by XSS, those tokens remain valid until expiry—and storing them in `localStorage` lets any injected script steal them silently.

## Solution
Match the token model to your architecture, and follow ASVS V7/V9 and RFC 8725:

- **Default to opaque server sessions** for classic web apps with one backend + Redis/Postgres: generate ≥ 128 bits of CSPRNG entropy, store the session server-side, and send it in an `HttpOnly; Secure; SameSite=Lax` cookie.
- **Use short-lived JWTs (5–15 min) + rotating refresh tokens** when downstream services must verify identity without calling an auth DB on every request:
  - Every `/refresh` call issues a **new** refresh token and marks the previous one used.
  - If an already-used refresh token is presented again (**reuse detection**), revoke the entire token family immediately—either the attacker or the legitimate user raced, so force re-login.
- **Storage rule:** Never put access or refresh tokens in `localStorage` or `sessionStorage` in a browser app; use `HttpOnly` cookies (with CSRF protection) or keep short-lived access tokens only in memory via a BFF (Backend-for-Frontend).
- **JWT verification rules (RFC 8725):** Pin allowed algorithms (`['EdDSA']` or `['RS256']`, never `none`), validate `iss`, `aud`, `exp`, and `nbf`, and sanitize `kid` so it can never trigger path traversal or arbitrary SQL/HTTP lookups.

## Real-world analogy
<Analogy>
A **server session** is a coat-check ticket: the number means nothing by itself, and the attendant can cross your number off the clipboard at any moment. A **JWT** is a signed, dated VIP wristband good for 15 minutes—bouncers at every door can verify the signature without calling the front desk, so you keep its expiry short and re-issue wristbands at a central booth.
</Analogy>

## Code
Pin the verification algorithm and claims explicitly—never accept `alg: none` or unvalidated `kid` headers:

```ts
// UNSAFE: trusts token header algorithm, skips issuer/audience checks
import jwt from 'jsonwebtoken';
const payload = jwt.decode(token); // decodes without verifying signature!

// SAFE: pins algorithm allowlist, issuer, and audience (RFC 8725 / ASVS V9)
import { jwtVerify } from 'jose';
const { payload: verified } = await jwtVerify(token, publicKey, {
  algorithms: ['EdDSA'],
  issuer: 'https://auth.example.com',
  audience: 'https://api.example.com',
});
```

## When to use / when to avoid
<Checklist
  use={[

## How to implement
<Steps>
  <Step>
    ### Regenerate session IDs on login
    Always issue a fresh session ID after authentication to prevent session fixation (ASVS V7).
  </Step>
  <Step>
    ### Keep access tokens short-lived
    Set access JWT `exp` to 5–15 minutes and validate `iss`, `aud`, `exp`, and `algorithms` on every API.
  </Step>
  <Step>
    ### Implement refresh rotation + reuse detection
    Store hashed refresh tokens with a `familyId` and `used` flag; revoke the family if a used token is replayed.
  </Step>
</Steps>
