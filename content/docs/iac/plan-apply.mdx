## TL;DR
`tofu plan` never guesses from `.tf` files alone: it loads your **configuration** and **prior state**, **refreshes** tracked resources against real infrastructure, computes the **diff**, and produces an execution **plan** that `tofu apply` executes and records into **new state**.

## Intent
<Intent>
Understand the exact data flow behind `tofu plan` and `tofu apply` so you can predict creates, in-place updates, replacements, and destroys—and avoid accidental state drift.
</Intent>

## Problem
If an IaC tool only read `.tf` files, it would have no way to know whether a resource already exists, which cloud ID corresponds to `local_file.manifest`, or whether someone changed a setting manually in the console. Without a state record, every run would risk recreating existing infrastructure or orphaning deleted resources.

## Solution
OpenTofu splits every change into a two-step preview-and-execute workflow:

1. **Read Config + Prior State:** OpenTofu parses `.tf` files to build the dependency graph and loads `terraform.tfstate` (local or remote backend) to find existing resource IDs.
2. **Refresh:** Providers query the real environment for every resource in state, updating the in-memory state snapshot with any out-of-band changes.
3. **Diff:** OpenTofu compares desired attributes in `.tf` against the refreshed state and marks each resource as no-op, create (`+`), update-in-place (`~`), replace (`-/+`), or destroy (`-`).
4. **Plan:** `tofu plan` prints the diff (and optionally writes a binary plan file with `-out=tfplan`) without mutating anything.
5. **Apply → New State:** `tofu apply` executes the planned provider calls in dependency order and writes the resulting attributes back to state.

## Real-world analogy
<Analogy>
Think of renovating a house with a blueprint (**config**) and an inspection clipboard (**prior state**). Before ordering materials, the contractor walks the rooms (**refresh**) to check what is actually there, compares the rooms to the blueprint (**diff**), hands you a written work order (**plan**), and only after you sign off does the crew build (**apply**) and update the as-built records (**new state**).
</Analogy>

## Code
Using the repo's `labs/tofu-local-file` project (note: `tofu` is not installed in this environment, so these commands are marked not run):

```bash
# Run against labs/tofu-local-file (not run — tofu binary not installed here)
cd labs/tofu-local-file
tofu init
tofu plan -var="environment=dev" -out=tfplan

```

## How to implement
<Steps>
  <Step>
    ### Initialize the working directory
    Run `tofu init` to download providers and configure the state backend.
  </Step>
  <Step>
    ### Generate and review a saved plan
    Run `tofu plan -out=tfplan` and inspect `+`, `~`, and especially `-` / `-/+` (destroy/replace) lines.
  </Step>
  <Step>
    ### Apply the exact plan
    Run `tofu apply tfplan` so no unexpected drift slips in between review and execution.
  </Step>
</Steps>
