## 1. Intent

<Intent>
Remote data is not your state. It is a copy of someone else's truth that is already stale when it arrives. TanStack Query makes that copy explicit: one typed key per resource, a deliberate freshness window, targeted invalidation, and a retry policy that only retries what can succeed.
</Intent>

## 2. Problem

Hand-rolled fetching with `useEffect` and three `useState` values looks fine in QA and fails in production. A slow earlier response lands after a fast later one and overwrites it, so one account's balance appears under another account's name. Three components mount with the same id and issue three identical requests. Every navigation re-fetches from cold. A single 503 is a permanent error. An unmount during flight writes state to a dead component. None of these are exotic; they are the five things a server-state library exists to prevent.

## 3. Solution

Split the world in two:

| | Client state | Server state |
|---|---|---|
| **Owner** | This tab | A remote system |
| **Truth** | You are the truth | You hold a copy |
| **Examples** | Drawer open, active tab, unsent input | Balances, transactions, profile, catalogue |
| **Needs** | Setter, maybe persistence | Caching, de-duplication, invalidation, retry, staleness |
| **Tool** | `useState`, `useReducer`, Zustand, URL | TanStack Query |

Then make three decisions per data type: **the key** (cache identity), **`staleTime`** (how long it is fresh), and **the invalidation target** (what a mutation touches).

## 4. Real-world analogy

<Analogy>
Think of a library's reading room. You can keep a photocopy of a reference book (the cache), but the shelf copy is the truth. A timestamp on the photocopy says how old it is (staleTime). When the librarian announces a new edition, every photocopy of that title is marked for replacement (invalidateQueries). You do not re-photocopy the whole library to update one book.
</Analogy>

## 6. Structure

A **key factory** is the invalidation API. Hierarchical keys let a prefix invalidate a whole subtree, so nothing else in the app writes a key literal:

```ts
export const accountKeys = {
  all: ['accounts'] as const,
  lists: () => [...accountKeys.all, 'list'] as const,
  detail: (id: string) => [...accountKeys.all, 'detail', id] as const,
  balance: (id: string) => [...accountKeys.detail(id), 'balance'] as const,
} as const
```

`accountKeys.detail(id)` invalidates that account's balance and transactions because prefix matching walks down; `accountKeys.all` nukes the domain. Choose freshness per data type and write down why:

| Data | `staleTime` | `gcTime` | Reason |
|---|---|---|---|
| Currency list, categories | `Infinity` | 24h | Changes on a release |
| Fee schedule, product terms | `60 * 60_000` | 24h | Editorial cadence |
| Profile, address | `5 * 60_000` | 30 min | Rarely changes |
| Transaction list | `30_000` | 10 min | New items matter, not sub-second |
| Available balance | `0` | `60_000` | A figure the user may act on |

## 7. When to use / when to avoid

<Checklist
  use={[
    "Any client-side server state in an authenticated app: balances, queues, profiles, search results.",
    "Screens that need background revalidation, optimistic updates or infinite scrolling.",
    "A read-mostly page that still needs an interactive refetch after first paint."
  ]}
  avoid={[
    "Read-only pages that never re-fetch: a Server Component `await` is simpler and ships no client cache.",
    "Genuine client state: drawer open, hover, unsent form text. Keep those in `useState` or the URL.",
    "Caching a per-user response under a key that omits the user - that is a data-disclosure bug."
  ]}
/>

## 8. How to implement

<Steps>
  <Step title="Make one query client per request">
    On the server, create a new `QueryClient` per request; in the browser, keep a single module-level instance. Never share a server client between users.
  </Step>
  <Step title="Define keys in one module">
    Use a typed key factory and import it everywhere, including mutations. Never hand-write a key string at a call site.
  </Step>
  <Step title="Set defaults deliberately">
    Choose a non-zero `staleTime`, `gcTime`, a retry function that skips 4xx, backoff with jitter, and `mutations.retry: 0`.
  </Step>
  <Step title="Validate at the boundary">
    Parse the response with a schema (Zod or generated) inside `queryFn`, so a shape change fails loudly instead of crashing a render.
  </Step>
  <Step title="Invalidate narrowly">
    After a mutation, invalidate the smallest prefix that changed. Use `setQueryData` when the response is the new resource, and `removeQueries` on logout.
  </Step>
</Steps>
