## TL;DR

- **Composition over configuration**: `children`/slots first, compound components second, `showX`/`variant` boolean piles last. React has no useful component inheritance.
- **Server Components are the default**; `'use client'` marks a boundary in the *module graph*, not one file. Push it to the leaves and keep the serializable-prop contract in mind.
- **Boundaries are architecture**: one `<Suspense>` + error boundary per independently valuable region, and memoization only after a Profiler measurement.

## Why it exists

A component starts as `<Table rows={rows} />`. Then requirements accumulate, and every stakeholder adds one more prop: `readOnly`, `hideReserve`, `selectable`, `extraColumns`, `disablePagination`. Now N booleans mean 2^N states you must be correct across, mutually exclusive combinations type-check fine, and a change for one consumer silently breaks another. The component isn't too big; it's **too configured**. Every new requirement widens one interface instead of adding one composition.

The same disease appears across a tree: data threading ("prop drilling") through five layers because a leaf needs one value, and the server/client split drawn at the route root so a heavy library meant for one leaf ships to the browser for the whole page.

## Mental model

**Three ways a parent influences a child, in order of preference:**

| Technique | Looks like | Cost |
|---|---|---|
| **Children / slots** | `<Panel header={<Title/>}>{rows}</Panel>` | None — parent owns the JSX, child owns layout |
| **Compound components** | `<Table><Table.Toolbar/><Table.Body/></Table>` | A context *internal* to the component family |
| **Configuration props** | `<Panel showHeader compact variant="legacy"/>` | Combinatorial: N booleans = 2^N states |

Rule of thumb: **a third boolean wanted a slot; a fifth drilled prop wanted composition (pass the rendered node down where data lives) or a scoped context.** Inheritance is not on the list — `extends` on a component was already a smell in 2019.

**Data access vs. rendering.** Keep server state in hooks (`useX`) or in Server Components, not in the markup component. A "presentational" component is pure and prop-driven — that's what makes it testable with a literal object. The old *container/presentational* split into two files is worth it only when the presentational half is reused with a *second* data source; a wrapper that only calls a hook and forwards props adds a layer with no behaviour. (See [data fetching](/docs/frontend/data-fetching-tanstack-query) for where server state belongs.)

**Server vs. client, precisely** (React official docs):

- **Server Components** run on the server, never ship to the browser, can `await` directly, can read secrets/databases/filesystem.
- **`'use client'` marks a boundary, not a file.** Everything imported transitively below it becomes client code. The directive is a root; push it to the *interactive leaf* (the toggle, the sortable header, the dialog trigger), never the page.
- **What crosses must be serializable**: strings, numbers, `bigint`, booleans, `null`, `undefined`, globally-registered symbols, iterables (arrays, `Map`, `Set`, `TypedArray`, `ArrayBuffer`) of serializable values, `Date`, plain objects, `Promise`s, **Server Functions**, and JSX. **Not** class instances, ordinary functions, or `Symbol('x')`.
- **A Client Component can receive server-rendered children**: `<ClientShell>{await <ServerTable/>}</ClientShell>` — the shell is interactive and tiny; expensive content stays on the server. This site uses exactly this for `<Flow>`.

**Memoization is a measurement, not a ritual.** `memo` earns its place when a component re-renders often with *identical props* and its render is *measurably expensive* (a 500-row grid, a chart). It's noise when a new object/callback identity arrives each render anyway. **React Compiler** (stable; opt-in in Next.js 16 via `reactCompiler`, which needs `babel-plugin-react-compiler`) applies memoization automatically; hand-written `memo`/`useMemo`/`useCallback` then become rare escape hatches. Reach for it after a React Profiler check, never before. *(This site does not enable React Compiler.)*

**Boundaries are failure + loading granularity.** One error boundary per *independently valuable region*; one `<Suspense>` per region that can resolve independently. A single boundary at the page root turns any panel failure into a blank page, and one `<Suspense>` around everything makes the fastest region wait for the slowest.

## Worked example (original)

A `<TaskBoard>` with three kanban columns. Bad: `showHeader`, `readOnly`, `disableDnD`, `extraActions`, `dense`, … Compose instead:

```tsx
// server component — no 'use client'
export default async function TaskBoardPage() {
  const tasks = await getTasks(); // runs on the server; fetching code never ships
  return (
    <Board tasks={tasks}>
      <Board.Header />
      <Board.Columns />
      <Board.EmptyState />
    </Board>
  );
}
```

```tsx
// components/board.tsx — compound component; context is scoped to the family
import { createContext, useContext, type ReactNode } from 'react';

type BoardCtx = { tasks: Task[] };
const Ctx = createContext<BoardCtx | null>(null);
const useBoard = () => {
  const c = useContext(Ctx);
  if (!c) throw new Error('Board.* must render inside <Board>');
  return c;
};

export function Board({ tasks, children }: { tasks: Task[]; children: ReactNode }) {
  return <Ctx.Provider value={{ tasks }}>{children}</Ctx.Provider>;
}
Board.Header = function Header() { return <h2>{useBoard().tasks.length} tasks</h2>; };
Board.Columns = function Columns() { /* reads useBoard(), no prop drilling */ return null; };
Board.EmptyState = function EmptyState() { return useBoard().tasks.length ? null : <p>Nothing here</p>; };
```

A variant that needs no header simply omits `<Board.Header/>`. No `showHeader` prop exists. Only the innermost interactive leaf (e.g. a `DragHandle`) needs `'use client'`. (Snippets shown for structure; not run.)

## Gotchas

- **`'use client'` at the top of `page.tsx`** ships the whole subtree's imports to the browser. Move it down to the interactive leaf.
- **Functions don't cross the boundary.** A `formatMoney` passed from a Server Component, or `onClick={fn}` from server to client, throws at render. Format on the server; pass serializable data; use a **Server Function** for mutations.
- **Classes don't serialize.** `new Decimal(...)`, `Map` subclasses, class instances fail; send `{ amount: "10.42", currency: "EUR" }`. (Plain `Map`/`Set`/`Date` are fine.)
- **A Client Component can still render on the server** for HTML, then hydrate; don't rely on `typeof window` during render. Use `useSyncExternalStore`, effects, or suppress hydration for browser-only values.
- **Stable `key`, never index.** `key={item.id}`; index keys reuse DOM nodes across reorders/filters — a checked checkbox or focus lands on the wrong record.
- **Hand-rolled memoization** without a Profiler measurement usually costs more than it saves.
- **One `<Suspense>`/error boundary** for the whole page hides partial failure and serializes loading.

## Production checklist

- [ ] Server Components by default; `'use client'` only on interactive leaves, at the top of that file.
- [ ] Props crossing the boundary are serializable; no server-only functions passed down; secrets stay server-side.
- [ ] `children`/slots tried before any boolean/variant prop; no component reaches a third boolean.
- [ ] Presentational components are pure; data access lives in hooks or Server Components; container split only if reused with a second source.
- [ ] `key` is a stable domain id; list reorder/filter keeps state on the right row.
- [ ] `<Suspense>` + error boundary per independently valuable region; fallbacks reserve layout.
- [ ] `memo`/`useMemo`/`useCallback` only after a Profiler check (or enabled React Compiler), not by default.
- [ ] Tests render presentational components with literal props; boundary contracts (throw outside parent) are asserted.
