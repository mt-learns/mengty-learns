## 1. Intent

<Intent>
The App Router has more than one rendering mode, and they can coexist inside one page. Choose **when** the HTML is computed and **whether it is shared** - then stream the regions that are slow. "Everything static" is not the goal; correctness is.
</Intent>

## 2. Problem

A public marketing page and a signed-in dashboard are not the same problem. Teams that apply one policy to both usually get one of two failures. Either they force a personalised page to be static and serve one user's data to another, or they make every page dynamic and pay server cost and latency for content that never changes. A third failure is subtler: one slow data source blocks the whole page because a single `await Promise.all` and a single error boundary turn six independent widgets into one fate.

## 3. Solution

Separate the two axes: **when** and **for whom**.

| Strategy | Rendered | Shared between users? | Good for |
|---|---|---|---|
| **SSG** (static) | At build time | Yes | Marketing, legal, help articles |
| **ISR** (revalidated) | At build, then background refresh | Yes, with a staleness window | Pricing, rate tables, published content |
| **SSR** (dynamic) | Per request on the server | No | Dashboards, statements, anything behind auth |
| **RSC** (Server Components) | On the server, streamed as payload | Depends on the data calls | The default component model in all of the above |
| **Streaming** | Shell first, regions later | Orthogonal | Any page where one region is slower than the rest |

The decision rule is one sentence: **if the output depends on who is asking, it is dynamic; if it is identical for everyone, it can be static or revalidated.** RSC and streaming are the mechanism, not alternatives to SSG/ISR/SSR.

## 4. Real-world analogy

<Analogy>
A bakery bakes and seals a batch once and every shop sells the same sealed loaf (SSG). If the recipe changes, the shop keeps selling the old batch until the new one arrives (ISR). A made-to-order sandwich with the customer's name on it is assembled per customer and never handed to someone else (SSR). Streaming is serving the bread while the sandwich filling is still being prepared.
</Analogy>

## 6. Structure

Route groups express the policy per segment:

```text
app/
  (marketing)/            # no URL segment, own layout
    page.tsx              # SSG
    pricing/page.tsx      # ISR: revalidate 3600, tag "pricing"
  (authenticated)/
    layout.tsx            # session check
    portal/
      page.tsx            # dynamic (reads cookies)
      loading.tsx         # streamed skeleton for this segment
      error.tsx           # client boundary for this segment
  api/
    webhooks/cms/route.ts # calls revalidateTag("pricing")
```

Be explicit about caching at the call site. Do not rely on version defaults that have changed before:

```ts
// Shared reference data: cache it, tag it, invalidate on publish.
await fetch(`${API}/products/motor/rates`, {
  next: { revalidate: 3600, tags: ['motor-rates'] },
})

// Personalised data: never cached, and say so.
await fetch(`${API}/brokers/${brokerId}/commission`, {
  cache: 'no-store',
  headers: { authorization: `Bearer ${token}` },
})
```

For non-`fetch` work, Next 16 offers the `use cache` directive with `cacheLife` and `cacheTag`; the older `unstable_cache` remains available for projects that have not adopted Cache Components. Either way, **every input that affects the output belongs in the cache key**. A function that reads `cookies()`, `headers()` or `auth()` must never sit behind a cross-request cache.

## 7. When to use / when to avoid

<Checklist
  use={[
    "SSG for content that only changes when you deploy: marketing, legal, documentation.",
    "ISR with a tag for content an editor changes on a schedule: pricing, catalogues, help centre.",
    "SSR for anything personalised or behind auth: dashboards, statements, approval queues.",
    "Per-region Suspense for a fast page with one expensive report or third-party widget."
  ]}
  avoid={[
    "Caching a response whose body depends on the request identity - that is a data-disclosure incident.",
    "One root-level error boundary and one Suspense around the whole page: it hides partial failure and serialises loading.",
    "Streaming a region whose fallback changes the layout - reserve the space or you trade a wait for a layout shift."
  ]}
/>

## 8. How to implement

<Steps>
  <Step title="Classify each route">
    Ask whether its HTML is safe to share. Write the answer next to the route (a comment, an ADR, a test) so the next engineer does not guess.
  </Step>
  <Step title="Make caching explicit">
    Put `revalidate` + `tags` on shared fetches and `cache: 'no-store'` on per-user fetches. Never inherit a default you did not choose.
  </Step>
  <Step title="Split slow regions">
    Move each independently useful region into its own async component behind `<Suspense>` with a fallback that matches the final layout.
  </Step>
  <Step title="Invalidate narrowly">
    After a write, prefer `revalidateTag('pricing')` over `revalidatePath('/')`, and `updateTag` when the user must see their own change immediately.
  </Step>
  <Step title="Test the boundary">
    Add a test that the per-user page never returns another user's data, and that the static route is in the prerender manifest.
  </Step>
</Steps>
